# 根目录

文中的文件引用都从项目根目录 `RM27_Client/` 写起。例如，`.vscode/settings.json` 是根目录下 `.vscode/` 文件夹中的配置文件。在 VS Code 中按 Ctrl+P 输入文件路径即可打开，查本文章节可按 Ctrl+F 输入标题。

本项目有两个可以分别启动的程序。桌面客户端是 C++17、Qt 6 和 QML 程序，入口在 `apps/client`，接收、解析和展示数据的代码在 `libs`。裁判模拟器是 Python 服务，自带一个浏览器控制台，入口在 `simulator/server`。在模拟模式下，浏览器通过 Socket.IO 修改模拟器状态，模拟器通过 MQTT 发布数据，桌面客户端向同一个 Broker（消息中转服务）订阅。网页的连接灯表示浏览器连到了 Python 服务。桌面端的“五类订阅就绪”表示 Broker 已同意订阅。哪条消息已经有可用数据，要看工作台对应主题的接收状态。

### 跟一次血量更新

以外部模拟器中**当前选中的机器人**为例。下面这些名称可以直接在对应文件中搜索。

1. 网页「机器人基础输入」中的血量输入框把值写入本行表单，`@change` 调用 `setBasicRobotFields(card.index)`。该方法把行下标、血量、热量和全局累计发弹量一起交给 `sendCommand`，通过 Socket.IO 发出 `referee_command`。这里传的是列表下标，机器人编号由服务端保存的顺序确定。`simulator/server/static/index.html` · `simulator/server/static/app.js`
2. 服务端在 `_apply_referee_command` 的 `set_basic_robot_values` 分支调用状态管理器。它校验输入，更新对应机器人的数据，并同步当前机器人视图。网页后续的 `update` 来自这一份状态快照，网页能回显只说明浏览器到模拟器这段已经生效。`simulator/server/app.py` · `simulator/server/state_manager.py`
3. 发布器从快照构造 `RobotDynamicStatus.current_health` 并向 Broker 发布。双方指定机器人的血量另在 `GlobalUnitStatus.robot_health` 中发布，前四项为己方，后四项为对方。当前机器人的卡片取前一个字段，所以查单车显示应从动态消息入手。`simulator/server/mqtt_publisher.py` · `libs/protocol/proto/rm27_base.proto`
4. 桌面端收到消息后，`MqttDataSource::drain` 在 Qt 线程把主题和字节交给 `protocol::decode`。五条订阅确认完成后，会话还要收到与本机配置编号相符且仍有效的 `RobotStaticStatus`，才会接纳这类不自带机器人编号的动态数据。`libs/transport/MqttDataSource.cpp` · `libs/protocol/BasicCodec.cpp` · `libs/application/ClientSession.cpp`
5. 会话通知界面状态变化。`ClientViewModel::healthText()` 从最新有效的动态样本取 `current_health`。缺失或过期显示「—」，收到合法的 0 就显示 0。工作台把 `healthText` 绑定到名为 `healthValue` 的文字控件。集成测试既检查解码值，也读取这个控件，能区分“收到了”和“显示出来了”。`libs/presentation/ClientViewModel.cpp` · `apps/client/qml/pages/OverviewPage.qml` · `tests/MqttReceiveCheck.cpp`

## .vscode

此目录保存 VS Code 的工作区配置。日常从状态栏按钮进入，也可以在命令面板选「任务：运行任务」按任务名执行。

### tasks.json

客户端有六个 `process` 任务，按 Debug / Release 各分构建、正式运行、模拟运行。它们以仓库根目录为工作目录，调用 PowerShell 并显式传给脚本配置名和模式。`RM27: Build Debug` 是默认构建任务，可用 Ctrl+Shift+B。客户端任务用 `$gcc` 匹配编译错误，便于从“问题”窗口跳到源码。`.vscode/tasks.json` · `scripts/build.ps1` · `scripts/run.ps1`

模拟器任务调用另一套脚本，提供安装、只启 Broker、启动服务、附带旧 UDP 或视频、环境检查、运行状态检查、停止及保留 Broker 等入口。“Start Video” 的文件提示来自本文件末尾 `inputs` 中 ID 为 `rm27SimulatorVideoFile` 的输入项，默认文本为 `resources/videos/testdemo.mp4`，按模拟器目录解析。修改某个任务实际执行的命令、参数或工作目录，从对应 `label` 的 `command/args/options` 入手。`.vscode/tasks.json` · `simulator/scripts/start.ps1`

### settings.json

`VsCodeTaskButtons.tasks` 把上述任务分成“构建”“运行”“裁判模拟器”三组按钮。`label` 是按钮上显示的文字，`task` 必须对应 `tasks.json` 中的任务名称。预览模式可从运行脚本选择，当前按钮提供正式和外部模拟两种。按钮的运行任务会启动程序，不附加调试器。`.vscode/settings.json` · `.vscode/tasks.json`

同一文件的 `cmake.cmakePath` 指定 VS Code 的 CMake Tools 扩展用哪个 `cmake.exe`。按钮经 PowerShell 构建时，脚本从本机预设的 `RM27_CMAKE_ROOT` 找程序。迁移工作区时如果按钮能构建而扩展找不到 CMake，分别核对这两个位置。`.vscode/settings.json` · `CMakeUserPresets.json`

## apps

`apps/client/` 是桌面客户端。阅读一次启动过程可以从 `apps/client/main.cpp` 进到 `apps/client/ClientApplication.cpp`，再看 `apps/client/qml/Main.qml`。要追工作台上的数字，可以反过来从页面查绑定的属性，再到 `libs/presentation/ClientViewModel.cpp` 和 `libs/application/ClientSession.cpp` 查来源。

### client

桌面程序的所有入口文件均在 `apps/client/`。这里的 `main.cpp` 是进程入口，`ClientApplication` 组装对象，`client.qrc` 把下面的 QML 与默认配置放入程序，`CMakeLists.txt` 把它们编成可执行文件。

#### qml

##### Main.qml

`apps/client/qml/Main.qml` 创建顶层 `ApplicationWindow`。C++ 在加载前传入必需的 `viewModel`，并设置标题和尺寸，QML 规定最小尺寸 640×480。窗口顶栏显示模式，启动出错时出现红色提示，最多显示四行，悬停可读完整错误。`TabBar` 的选中项决定 `StackLayout` 显示“工作台”还是“运行信息”，两个页面使用同一个 ViewModel。改导航、顶栏、窗口最小尺寸或底部模式提示从这里入手。

##### components

###### InfoCard.qml

`apps/client/qml/components/InfoCard.qml` 是页面共用的卡片外观格式。`Frame` 负责边框、背景和留白，`ColumnLayout` 从上到下显示必填的 `heading`、有内容才显示的 `value`、可换行的 `description`。调用方可把 `valueObjectName` 设成稳定的对象名，例如工作台把血量标签命名为 `healthValue`，界面检查程序便能找到控件并读取它实际显示的文字。**卡片外观在此统一修改**，数值和说明来自使用它的页面。`tests/MqttReceiveCheck.cpp`

##### pages

###### OverviewPage.qml

`apps/client/qml/pages/OverviewPage.qml` 是“工作台”。顶部显示数据源说明、连接状态和详细信息。“启动数据源”和“停止”按钮根据 `canStart`、`active` 决定能否点击，通过 `viewModel.start()`、`stop()` 操作会话。最近诊断单独显示。MQTT 模式下，四张卡片展示本机动态状态、静态身份、比赛阶段和己方经济，下方另列全局单位摘要和五类消息的接收状态。`Repeater` 按 `topicStates` 逐条显示未收到、已收到或已过期。预览模式下换为心跳序号和运行秒数。整个区域可滚动，卡片网格在可用宽度达到 900 时排两列，否则一列。页面决定“放在哪里”，各项摘要文字的拼法见 `libs/presentation/ClientViewModel.cpp`。

###### DiagnosticsPage.qml

`apps/client/qml/pages/DiagnosticsPage.qml` 是“运行信息”。从同一个对象读取模式、来源、日志文件路径和最近一条诊断。路径用可选中复制的只读文本框显示，配置文件或身份变更需要重启客户端才会生效。逐消息状态在工作台，本次已记录的启动、连接变化、诊断和退出事件可在该路径的 JSONL 文件中查看。事件的生成处见 `apps/client/ClientApplication.cpp`，落盘格式见 `libs/diagnostics/JsonlLogger.cpp`。

#### client.qrc

`apps/client/client.qrc` 是 Qt 资源清单，在前缀 `/RM27/Client` 下为入口、两页、一张卡片和 `configs/defaults.json` 分配别名。根工程开启 `AUTORCC`，构建时将这些源文件编入可执行文件。QML 引擎用 `qrc:/RM27/Client/Main.qml` 打开入口，配置加载器用 `:/RM27/Client/defaults.json` 读取内嵌默认值。页面中的 `import "pages"`、`import "../components"` 依赖资源内部的相对目录。新增本地 QML 时要对照本清单及页面引用。修改内嵌文件后要重新构建，外部 `--config` 文件则在下次启动时读取。

#### ClientApplication（.cpp 与 .h）

`apps/client/ClientApplication.h` 声明应用组装入口 `ClientApplication::run(QGuiApplication&)`。`apps/client/ClientApplication.cpp` 实现其执行顺序。

1. 选 Qt Quick Controls 的 `Basic` 样式，读取 `--config` 与 `--log-dir`，把配置文件路径交给 `libs/config/AppConfig.cpp` 中的 `loadConfig()`。配置读取失败时使用默认窗口尺寸显示出错文件和原因。
2. 生成 `client-<UTC日期与时间，含毫秒>-<进程号>.jsonl`。日志目录先看 `--log-dir`，相对路径以进程当前目录为基准。其次看 `logging.directory`，相对路径以外部配置所在目录为基准，内嵌配置则取当前目录。两者都未指定目录时使用 Qt 提供的应用本地数据目录下的 `logs`。打开或首次写入失败会在窗口显示启动错误。配置有效时，日志错误仍允许数据源启动。
3. 依据配置选择数据源。`preview` 建 `MockDataSource`（`libs/transport/MockDataSource.cpp`），`official`、`simulation` 都建 `MqttDataSource`（`libs/transport/MqttDataSource.cpp`），无效配置才建 `UnavailableDataSource`（`libs/transport/UnavailableDataSource.cpp`）。随后创建 `ClientSession`（`libs/application/ClientSession.cpp`），设置配置的机器人 ID 和来源说明，把会话状态、诊断分别记为 `session.state`、`session.diagnostic`。
4. 创建 `ClientViewModel`（`libs/presentation/ClientViewModel.h`），注册 `RM27.Client 1.0` 供 QML 识别其类型，将对象所有权留给 C++。引擎设置初始属性，再加载 `apps/client/qml/Main.qml`。根对象加载失败会尝试记 `client.qml_failed` 并返回 1。成功且配置有效才自动启动会话。事件循环退出时停止会话并记录 `client.stop`。数据源先于会话创建，QML 最先销毁，避免页面或会话在退出时访问已经释放的对象。

#### CMakeLists.txt

`apps/client/CMakeLists.txt` 用 `qt_add_executable` 定义 Windows GUI 目标 `RM27_Client`，编入入口、组装代码和资源，链接配置、日志、传输、展示、协议模块及 Qt Gui、Qml、Quick、QuickControls2。根工程版本被定义为 `RM27_VERSION`，应用输出到对应构建目录的 `bin`。开启 `BUILD_TESTING` 时另建 `RM27_SessionCheck` 并注册 CTest 名 `basic_session`，以及复用真实 QML 资源的 `RM27_MqttCheck`，后者由接收检查脚本驱动。`tests/BasicSessionCheck.cpp` · `tests/MqttReceiveCheck.cpp` · `scripts/check-mqtt-receive.ps1`

#### main.cpp

`apps/client/main.cpp` 是操作系统调用的进程入口。创建 `QGuiApplication`，设置组织名 `RM27`、程序名 `RM27_Client` 和构建时写入的版本，调用 `ClientApplication::run(app)` 并返回其退出码。查实际启动、配置或连接失败应继续读 `apps/client/ClientApplication.cpp`。

## build

这个目录由配置、编译和检查过程写入。查实现时从同名的源码目录进入，例如 `build/local-debug/libs/protocol` 对应根目录下的 `libs/protocol/`。

### dependency-downloads

| 源码压缩包                        | 这个项目用它做什么                                                                                                                                                                                                                                          |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `paho-mqtt-c-v1.3.15.tar.gz` | **接收消息。** Eclipse Paho MQTT C 提供异步 MQTT 客户端库。桌面端的 `MqttDataSource` 用它连接 Broker、订阅主题并取得收到的字节。所链接的目标是 `paho-mqtt3a-static`。见 `libs/transport/MqttDataSource.cpp`、`libs/transport/CMakeLists.txt`。                                                    |
| `protobuf-v29.3.tar.gz`      | **读懂消息。** 这份源码生成两个项目会用到的东西。构建时，工具 `protoc` 把 `libs/protocol/proto/rm27_base.proto` 转成 C++ 消息类。运行时，协议库通过这些类和 `libprotobuf` 把消息字节还原成字段，例如从 `RobotDynamicStatus` 读出 `current_health`。见 `libs/protocol/CMakeLists.txt`、`libs/protocol/BasicCodec.cpp`。 |

## cmake

这里是根 `CMakeLists.txt` 在配置阶段依次 `include` 的两个依赖脚本。它们暂时关闭 Qt 的自动元对象和资源处理，引入纯 C/C++ 第三方工程后恢复，随后继续配置自己的 Qt 目标。

### Protobuf.cmake

定义共用下载目录变量 `RM27_DEPENDENCY_DOWNLOAD_DIR`。先引入 Abseil，再用同一套客户端编译器构建 Protobuf 的静态运行库与 `protoc` 生成器，关闭上游示例、测试和安装等选项。`protoc` 在编译协议库时将项目的 `.proto` 转成 C++。运行库负责实际的字节解析与序列化。离线使用指定版本的解包源码时，可按脚本注释设置对应的 `FETCHCONTENT_SOURCE_DIR_*` 变量。Python 绑定有单独的生成入口。`cmake/Protobuf.cmake` · `libs/protocol/CMakeLists.txt` · `simulator/tools/release/generate_base_protobuf.py`

### PahoMqtt.cmake

### domain

这一层定义 C++ 中的数据含义。接收层、会话层和界面通过相同的数据结构交接，字段是否存在、何时接收和如何展示分别由不同对象负责。

- `BasicData.h` 定义五种消息内容：`GameData` 存局号、比分、阶段、时间与结算。`GlobalUnitData` 存双方单位、基地与前哨状态、按槽排列的单位值及全局统计。`LogisticsData` 存当前/累计经济、科技和加密等级。`RobotStaticData` 存身份、在场/存活状态、等级和性能上限。`RobotDynamicData` 存当前状态、经验、资源及可用标志。`BasicMessage` 用 `std::variant` 容纳其中一种，标量用 `std::optional` 区分零/否和字段缺失，重复字段保留为向量。字段的协议编号、编码类型在 `libs/protocol/proto/rm27_base.proto`。
- 同一文件的 `identifyRobot` 从 ID 取得阵营和角色，`RobotStaticData::role()` 优先用已知 ID，才用原始 `robot_type` 推测角色。后者单独保留原值，不能补造 ID 或阵营。`healthRobotIds` 和 `bulletRobotIds` 分别提供八项双方血量、六项己方数组的界面标签。蓝方视角调整己敌顺序，六槽中的 2/102 保留。六槽顺序、静态类型的本地解释分别按 P-002、P-003 的指定范围使用，具体依据见 `docs/planning/09_Open_Questions.md`。展示逻辑见 `libs/presentation/ClientViewModel.cpp` 中的 `unitsSummary()` 和 `robotIdentityText()`。
- `BasicState.h` 定义 `BasicSample<T>`：可选的最新值 `value`、过期标记 `stale` 和按本次会话计的本地接收毫秒 `receivedAtMs`。`BasicState` 为上述五类消息分别保存一份。时间由 `ClientSession`（`libs/application/ClientSession.cpp`） 维护，可以区分从未收到、已经收到、先收到后过期。
- `ClientSnapshot.h` 保存内置演示心跳的 `sequence`（序号）和 `elapsedSeconds`（预览运行秒数），由 `MockDataSource`（`libs/transport/MockDataSource.cpp`） 生成。虽然名字叫 Snapshot，这个结构只服务预览。
- `、ConnectionState.h` 定义 `Disconnected`、`Connecting`、`Subscribing`、`Connected`、`Unavailable` 五种连接状态。MQTT 接通 Broker 后还会停留在 `Subscribing`，五种订阅全部获准才进入 `Connected`。每个主题是否已经收到数据另查 `BasicState`。
- `RunMode.h` 声明 `Official`、`Simulation`、`Preview` 和字符串转换接口。`libs/domain/RunMode.cpp` 的 `parseRunMode` 仅识别对应的小写字符串，未知值返回空。输入来自 `libs/config/AppConfig.cpp`，选择实际数据源见 `apps/client/ClientApplication.cpp`。
- `CMakeLists.txt` 构建 `rm27_domain` 静态库，公开 `libs` 作为头文件搜索目录，使上层可写 `#include "domain/BasicData.h"`。模块使用普通 C++ 类型并关闭 Qt 的 `AUTOMOC`。`BasicState.h` 由使用方经头文件包含。

### protocol

从网络取到一条 MQTT 消息后，`libs/transport/MqttDataSource.cpp` 把主题和负载交给协议层。网络上的负载是一条 Protobuf 消息的二进制内容。选用哪种消息格式由主题名决定。协议层只负责字节与 C++ 数据的转换。成功后，会话才会检查机器人身份、保存各主题状态并通知界面。`libs/domain/BasicData.h` · `libs/application/ClientSession.cpp`

| 文件                                                      | 代码和用途                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `proto/rm27_base.proto`                                 | 客户端和模拟器共同使用的 RM27 基础消息定义，`rm27.wire` 是生成代码的命名空间。五种消息分别描述比赛进程、全场单位状态、经济与技术状态、本机静态身份及能力、本机实时状态。每一项后面的数字是线上字段编号。标量使用 `optional`，可以区分“本包没给”和“明确给了 0 / false”。两组机器人数组用 `repeated`。字段定义、类型和编号从这里查，数组各位置对应的机器人和角色解释在 `libs/domain/BasicData.h`。                                                   |
| `BasicCodec.h`                                          | 暴露主题契约 `TopicContract`（主题名、频率、最大 QoS），以及 `contractFor`、`decode` 和 `encode`。解码结果装一条可选的 `domain::BasicMessage` 或错误说明。编码结果带有主题、字节和错误说明。                                                                                                                                                       |

| `CMakeLists.txt`                                        | 调用 `protobuf::protoc` 从同一份 .proto 生成 C++ 的 `rm27_base.pb.h/.cc`，写在当前构建目录的 `libs/protocol/generated/` 下，与 BasicCodec 一起编成静态库 `rm27_protocol`。开启 `BUILD_TESTING` 时另外生成 `RM27_ProtocolCheck` 并向 CTest 注册 `protocol_basic`。Python 生成物的入口在 `simulator/tools/release/generate_base_protobuf.py`。 |
| `tests/BasicCodecCheck.cpp`                             | `selfTest` 用固定字节而非只用自身编码结果，验证字段号、带符号的倒计时、显式 false、uint64 上界、数组视角、类型回退及未知值，覆盖截断报文、非法字段、错误数组长度和 NaN。程序无参数时跑自检。`--decode` 读文件并输出 JSON，`--decode-role` 进一步输出静态角色解释，`--emit-fixtures` 导出 C++ 编码样本。后面三种方式供 `tests/check_basic_data.py` 调用。                                                       |

#### 五条消息在各层叫什么

MQTT 层靠主题名选择解码器，会话按类型保存最新样本，QML 绑定展示属性。找同一个字段时可以横着读表。

| MQTT 主题                 | 领域类型 → `BasicState`               | 展示入口                                           |
| ----------------------- | --------------------------------- | ---------------------------------------------- |
| `GameStatus`            | `GameData → game`                 | `gameText`、`gameSummary`，比赛阶段、比分、计时与结算         |
| `GlobalUnitStatus`      | `GlobalUnitData → units`          | `unitsSummary`，双方设施、双方指定机器人的血量和己方六槽累计发弹量       |
| `GlobalLogisticsStatus` | `LogisticsData → logistics`       | `economyText`、`logisticsSummary`，当前与累计经济等      |
| `RobotStaticStatus`     | `RobotStaticData → robotStatic`   | `robotIdentityText`、`staticSummary`，身份、角色和性能上限 |
| `RobotDynamicStatus`    | `RobotDynamicData → robotDynamic` | `healthText`、`dynamicSummary`，当前血量等实时值         |

字段号见 `libs/protocol/proto/rm27_base.proto`，五份样本见 `libs/domain/BasicState.h`，从成员取值并转成界面文字的实现见 `libs/presentation/ClientViewModel.cpp`。

### application

- `libs/application/IDataSource.h` 定义所有数据源共同的 `QObject` 接口。调用方用 `start()/stop()` 控制生命周期，通过 `connectionChanged` 收连接状态、`snapshotReceived` 收预览心跳、`basicMessageReceived` 收解码后的基础消息、`diagnosticReceived` 收诊断。`ageMs` 表示报文从本机网络接收至交给会话的时长，包含等待订阅确认、等待 Qt 处理的时间。文件还声明信号所用领域类型的 Qt 元类型。三个具体实现见 `libs/transport/`。
- `libs/application/ClientSession.h` 声明会话持有的数据源引用、运行标志、连接详情、预览快照、五类基础状态、身份和最近诊断，向展示层提供只读访问及变化信号。数据源由 `ClientApplication`（`apps/client/ClientApplication.cpp`） 创建并保证活得比会话久。`configureIdentity` 只在停用状态接收配置。
- `libs/application/ClientSession.cpp` 连接上述信号、注册元类型。`start` 清空上次数据和诊断、启动计时后调用数据源。`stop` 先关闭本次接收入口再停数据源，清掉快照和五类值。断线、失败也会清空数据。`acceptBasicMessage` 仅在活动且连接就绪时接纳业务数据，按主题替换整份样本，其他主题的值保留。同主题新消息省略某字段时，该字段恢复为未知。
- 比赛状态可独立保存。静态身份的 `robot_id` 须与配置一致，缺失或不符会清掉静态、动态、全局单位、后勤样本并给出诊断，比赛状态保留。动态、单位、后勤三类须在本会话已有匹配且仍有效的静态身份后才能采纳。`refreshFreshness` 每 250 毫秒检查各主题：比赛/动态 1000 毫秒，单位/后勤/静态 3000 毫秒。抵达会话前已排队太久的包也会直接标记过期。这些是客户端诊断阈值。规则依据另查 `libs/protocol/CONTRACT.md`。相关边界在 `tests/BasicSessionCheck.cpp` 有具体样例。
- `libs/application/CMakeLists.txt` 构建 `rm27_application`，公开依赖 `rm27_domain` 和 Qt Core，具体网络接收器由外部传入。因此会话检查可以直接使用测试数据源覆盖身份、过期与重复启停。

### config

- `libs/config/AppConfig.h` 定义窗口、心跳、日志和 MQTT 配置及其 C++ 默认值。`AppConfig` 汇总这些结构，`ConfigResult` 携带解析成功后的配置或可读错误。窗口默认 1280×800、预览间隔 1000 毫秒，日志目录默认留空，由应用决定最终位置。客户端每次读一份 JSON。启动参数省略 `--config` 时读 `configs/defaults.json`，指定时读外部文件。`loadConfig` 从 C++ 默认值开始，按模式确定默认主机，再用选中那份 JSON 的显式字段覆盖。
- `libs/config/AppConfig.cpp` 的 `loadConfig` 同时支持 Qt 资源路径和磁盘路径。读取失败带文件位置，JSON 语法错误带字节偏移，未知键、类型或范围错误带字段说明。根必须是对象，`mode` 必填。可选对象有 `window`、`simulation`、`logging`、`mqtt`，各层只接受已列的字段。`official` 默认地址 `192.168.12.1`，`simulation` 省略地址时为 `127.0.0.1`。端口 1–65535，超时和心跳间隔 100–60000 毫秒，机器人 ID 接受 1、3–9 及蓝方加 100 的对应号。窗口宽 640–7680、高 480–4320，标题须为去掉首尾空白后仍非空的字符串。增加或排查配置项应同时参照头文件的默认值、这里的允许字段与校验，以及 `configs/` 中相应示例。
- `libs/config/CMakeLists.txt` 构建 `rm27_config` 静态库，链接 `rm27_domain` 和 Qt Core 以读取 JSON、识别模式和机器人身份。桌面程序和会话检查都使用同一个配置加载器。

### transport

- `libs/transport/MqttDataSource.h` 声明五主题 MQTT 接收器，构造参数来自配置的地址、端口、机器人 ID 和超时。`Context` 管理一次连接的 Paho 回调和缓存，`generation_` 区分各次启动。类中还保存 Qt 轮询计时器、DNS 查询编号和连接、订阅、就绪标志。
- `libs/transport/MqttDataSource.cpp` 的 `start` 直接使用 IP 或通过 Qt 异步解析主机名，有 IPv4 时优先选用。`connectAddress` 通过 Paho 异步 C 库建立 MQTT 3.1.1 TCP 连接，以机器人 ID 的十进制文本为 clientID，使用干净会话。`subscribe` 分别申请五个主题、请求 QoS 1。五份订阅确认都返回可接受的 QoS（0 或 1）后才发送就绪状态。连接和等待订阅确认分别计时。出错时释放连接、上报原因，恢复后可从界面重新启动。
- Paho 回调在 `Context::messageArrived` 按实际长度精确匹配主题，过滤保留消息、异常 QoS 和超出 1 MiB 工程接收上限的负载。回调只写有锁的缓存。比赛、动态、单位、后勤各保留最新一条，静态身份因决定后续数据的归属而按到达顺序最多保留八条，超过上限终止会话并报告积压。Qt 对象线程的 `drain` 每 20 毫秒读取缓存，等订阅全部获准后将待处理消息按到达序号排序，调用 `protocol::decode`（`libs/protocol/BasicCodec.cpp`），把成功结果和本地排队时长交给会话。解码失败、保留消息或无效负载产生诊断，可从 `apps/client/qml/pages/DiagnosticsPage.qml` 查看。`release` 取消 DNS、停止轮询、使旧回调失效、销毁 Paho 客户端，随后再释放上下文。
- `libs/transport/MockDataSource.h` 声明预览用定时器、计时器和序号。`libs/transport/MockDataSource.cpp` 的 `start` 把序号清零然后立即发第一份快照（序号 1），此后每个间隔发序号和累计运行秒数。停止时关定时器并清零，下次从头计。由 `configs/preview.example.json` 选用，整个过程在客户端自身完成。
- `libs/transport/UnavailableDataSource.h` 和 `libs/transport/UnavailableDataSource.cpp` 是无连接占位实现。其 `start/stop` 只发不可用或已断开状态。头文件沿用早期“正式模式占位”的注释。以当前 `apps/client/ClientApplication.cpp` 的实例化条件为准，它仅用于配置失败路径，此时会话也不会自动启动。配置有效的官方模式走真正的 MQTT 接收器。
- `libs/transport/CMakeLists.txt` 把三个适配器编成 `rm27_transport`，公开 `rm27_application`，用 `PRIVATE` 链接 `rm27_protocol`、Qt Network 和 `paho-mqtt3a-static` 并定义 `PAHO_MQTT_STATIC`。查 Paho 版本或库的获取入口见 `cmake/PahoMqtt.cmake`。

### presentation

- `libs/presentation/ClientViewModel.h` 是 C++ 提供给 QML 的界面接口。`Q_PROPERTY` 列出模式、连接文案、按钮可用性、预览心跳、基础数据摘要、逐主题状态、启动错误、日志路径。`NOTIFY` 指定对应变化信号，供 QML 自动刷新。`Q_INVOKABLE start/stop` 是按钮入口，`basicEvidence()` 让 `tests/MqttReceiveCheck.cpp` 取得和界面相同的一组格式化数据。
- `libs/presentation/ClientViewModel.cpp` 将会话四组信号转为 QML 属性更新。`fresh/status/number` 决定过期与未收到的提示、横线占位，以及合法零值、布尔值和浮点数的显示。`gameText/gameSummary` 翻译阶段并显示局数、比分、时间和暂停，仅在结算阶段显示结果和原因。`robotIdentityText/staticSummary` 展示身份、角色、状态、等级与上限。`healthText/dynamicSummary` 读动态样本，保留单位待确认字段的原值说明。`economyText/logisticsSummary` 读后勤。`unitsSummary` 按配置阵营标注数组中的机器人 ID，并保持红、蓝前哨的固定标记。未识别的枚举可显示原始数字。`topicStates` 为五类主题各返回名称、接收状态、是否收到、是否过期和本地接收毫秒。界面绑定位置见 `apps/client/qml/pages/OverviewPage.qml`。
- `libs/presentation/CMakeLists.txt` 构建 `rm27_presentation`，依赖会话模块和 Qt Core。QML 注册和实例创建留给 `apps/client/ClientApplication.cpp`，从而让界面检查程序可以复用同一 ViewModel。

### diagnostics

- `libs/diagnostics/JsonlLogger.h` 声明 `open(path)`、`write(level,event,detail)`、`errorString()`，对象保存文件及最近的错误原因。`libs/diagnostics/JsonlLogger.cpp` 负责创建父目录、以追加方式打开文件、每次写一个紧凑的 JSON 对象加换行并刷新。每行有 UTC 毫秒级 `timestamp`、`level`、`event` 和 `detail`。目录创建、打开、写入或刷新失败都可查到错误说明。该类负责落盘。文件名、目录选择、记录哪些事件由 `apps/client/ClientApplication.cpp` 决定。某次运行的实际路径显示在 `apps/client/qml/pages/DiagnosticsPage.qml`。
- `libs/diagnostics/CMakeLists.txt` 将日志实现编为 `rm27_diagnostics`，仅依赖 Qt Core。这里的日志记录启动、状态变化和诊断等事件。逐主题的内存状态属于 `ClientSession`（`libs/application/ClientSession.cpp`）。

### video

`libs/video/README.md` 是图传资料索引，链接架构边界、UDP 覆盖记录及测试视频入口。该目录目前只有这份说明，`CMakeLists.txt` 中也没有 `rm27_video` 目标。独立模拟器的视频发送与资源位于 `simulator/server/video_streamer.py` 和 `simulator/resources/videos/`。

## scripts

根目录这四个 PowerShell 脚本管理**桌面客户端**的编译、运行与检查。独立模拟器的启停入口在 `simulator/scripts/`。下例均以项目根目录为当前目录。

### build.ps1

`-Configuration Debug|Release` 选择 `local-debug` 或 `local-release`，默认 Debug。`-Jobs` 允许 1–256，默认取逻辑处理器数和 8 中的较小值。脚本读取本地预设的四个工具根目录，逐项检查实际程序或 DLL，再检查同一构建目录的客户端是否正在运行。随后先执行 CMake 配置、再构建。每一步的退出码都决定是否继续。构建本身不会启动 GUI。点击按钮时两次 CMake 调用如何串起来，见本文 `CMakeUserPresets.json` 一节。`scripts/build.ps1`

### run.ps1

默认先调用 `build.ps1` 增量构建，再启动相应 `bin/RM27_Client.exe`。`-SkipBuild` 使用已有可执行文件和 `CMakeCache.txt`。脚本从缓存读 `Qt6_DIR`、`CMAKE_CXX_COMPILER`，临时把配套 Qt、MinGW 的 `bin` 加入 PATH，等待 GUI 退出后恢复环境。若缺 DLL 或版本不匹配，应先确认启动的配置和缓存中记录的工具路径。`scripts/run.ps1` · `configs/`

```powershell
.\scripts\build.ps1 -Configuration Debug
.\scripts\run.ps1 -Configuration Debug -Mode preview -SkipBuild
```

这个例子先生成 Debug 程序，再用本地心跳看界面。改用 `-Mode simulation` 会选择连接外部 Broker 的示例配置。有自己的 JSON 时用 `-ConfigFile`，日志位置可用 `-LogDirectory` 覆盖。程序接收的命令行选项名为 `--config`、`--log-dir`。`scripts/run.ps1` · `apps/client/ClientApplication.cpp`

### check-basic-data.ps1

依次运行三组检查：CTest 的 `protocol_basic` 验证 C++ 字节解析。`tests/check_basic_data.py` 让 Python 与 C++ 程序读写彼此的样本。`simulator.tools.check_base_data` 检查模拟器生成数据及网页命令处理。脚本默认先构建，也可传 `-SkipBuild`。CTest 和 Qt 工具路径来自构建缓存，Python 固定取模拟器的虚拟环境。这条入口适合定位“两个程序对字段编号、类型或数组顺序理解是否相同”。`scripts/check-basic-data.ps1` · `libs/protocol/tests/BasicCodecCheck.cpp` · `tests/check_basic_data.py` · `simulator/tools/check_base_data.py`

### check-mqtt-receive.ps1

先检查构建缓存、模拟器虚拟环境和测试专用依赖，再运行 CTest 的 `basic_session`，随后把 `RM27_MqttCheck.exe` 及循环次数交给 Python 联调驱动。`-Cycles` 默认 100、范围 1–1000。`-Configuration` 和 `-SkipBuild` 与基础检查相同。此入口覆盖模拟器网页事件、实际 MQTT 传输、客户端接收与 QML 显示，使用临时本机服务，输出证据目录。需运行它时，模拟器正常安装之外还需要 `pyproject.toml` 中的 `test` 依赖。`scripts/check-mqtt-receive.ps1` · `simulator/pyproject.toml` · `tests/BasicSessionCheck.cpp` · `tests/check_mqtt_receive.py`

### docker

- `simulator/docker/docker-compose.yml` 只编排 `broker` 服务，使用 Mosquitto 2 镜像。默认把宿主机回环地址的 3333 映射到容器 1883，`RM_SIM_MQTT_PORT` 可覆盖宿主机端口。它还挂载代理配置并定义容器内部的健康检查。Python 网页服务由 `simulator/scripts/start.ps1` 单独启动。
- `simulator/docker/mosquitto.conf` 配置容器内监听、允许匿名的本地模拟、关闭消息持久化，将带时间戳的错误、警告和通知日志输出到标准输出。网络接收测试默认使用 Python 临时 AMQTT。若要定位 Docker 部署的连接问题，应查看这里和上面的宿主机端口映射。

### server

`main.py` 处理命令行，`app.py` 装配服务，`state_manager.py` 保存状态，`mqtt_publisher.py` 把状态编码发给 Broker。跨到 Qt 的完整例子见本文“跟一次血量更新”一节。

#### 启动与网页接口

- `simulator/server/__init__.py` 声明 `simulator.server` 包，使脚本和测试可以导入服务端组件。导入包时不会绑定端口。
- `simulator/server/main.py` 是 `python -m simulator.server.main` 入口。`simulator/scripts/start.ps1` 最终从这里进入 Python 服务。默认网页监听 `127.0.0.1:8000`，模拟器则主动连接 `127.0.0.1:3333` 上的 MQTT Broker。`build_parser` 接受环境变量和命令行覆盖，校验端口和机器人编号。`--check` 只检查 Python 版本、依赖、两份 Protobuf 绑定、配置和网页资源，同时报告 FFmpeg、Docker 是否可找到。`--probe-mqtt` 单独检查 Broker 能否接受 MQTT CONNECT。正常启动时先试绑网页地址，调用 `create_app`，再由 Uvicorn 接管服务和退出请求。
- `simulator/server/app.py` 将接口与各组件接起来。`create_app` 建立状态管理器、赛事演示引擎、FastAPI 和 Socket.IO。`lifespan` 在服务启动时连接 MQTT，开启状态线程、两路等待操作的视频线程、按参数启用的旧 UDP 组件以及两个网页广播任务。退出时取消任务、停止各组件。启动时 MQTT 连接失败，网页仍能打开。网页上的连接灯反映浏览器与模拟器的连接，Broker 的实际连接状态见 `GET /api/health` 中的 `mqttConnected`。
- 同一文件中的 `_apply_referee_command` 按网页发来的 `command` 分派给状态管理器或具体工具。`referee_command` 把基础字段校验错误通过回执发回表单。切换当前机器人会更新状态管理器、MQTT 发布器和已启用的 UDP 发送器。提交机器人静态或动态状态会立即调用发布器，MQTT 已连接时才实际发送。`simulation_control` 驱动独立的赛事演示。`common_command` 保留了旧版模拟复活请求及回执。
- `_build_console_state` 把比赛快照、可选视频、普通图传状态和工业相机状态合并。网页连接时立即收到完整状态，之后 `broadcast_state` 每 0.5 秒广播一次 `update`。运行中的自动演示还会单独广播 `simulation_frame`。`GET /api/state` 返回相同结构。`GET /api/health` 还返回实例标识、当前机器人及五个基础主题。`POST /upload` 保存视频后广播更新，`POST /api/shutdown` 供带本机身份校验的 `simulator/scripts/stop.ps1` 使用。根路径最后挂载 `simulator/server/static/`，这些 API 优先于静态文件匹配。

#### 从一次网页操作查到实际状态

| 看到的现象 | 要追的代码 |
| --- | --- |
| 网页提示输入失败 | `referee_command` 调用 `_apply_referee_command`。基础字段出现类型、范围或溢出错误时，服务端返回 `{ok: false, error: …}` 并记日志。`sendCommand` 把错误写进 `baseInputError`，页面基础数据区用 `role="alert"` 显示。`simulator/server/app.py` · `simulator/server/static/app.js` · `simulator/server/static/index.html` |
| 网页已经接受修改，要确认哪些值生效 | 成功回执 `{ok: true}` 表示命令处理已返回。服务端还会广播 `update`，带回从 `StateManager` 重新读取的状态。桌面端通过 MQTT 取得数据。定位两边显示的差异，可依次比对 `GET /api/state`、发布器构造的消息和 Qt 工作台的逐主题接收状态。`simulator/server/app.py` · `simulator/server/mqtt_publisher.py` · `apps/client/qml/pages/OverviewPage.qml` |
| 一个网页切换操作方，另一个窗口显示的机器人也变了 | 浏览器保存上次选择的 `currentRobotId`，连接时可将它作为 `set_current_robot` 提交。`select_robot` 切换整个模拟器实例的当前机器人，各窗口都会从快照收到这个编号。桌面端接收哪个编号的数据由启动配置中的 `mqtt.robotId` 决定。`simulator/server/static/app.js` · `simulator/server/state_manager.py` · `libs/config/AppConfig.cpp` |
| 网页 JSON 中的 `gameStatus` 有经济字段，在 MQTT 同名消息里找不到 | `get_state()` 为兼容网页，把后勤字段也合入 `gameStatus`，并用十进制字符串导出累计经济，以保留大整数的精度。MQTT 发布器为五个主题分别选字段，桌面端的累计经济来自 `GlobalLogisticsStatus.total_economy_obtained`。`simulator/server/state_manager.py` · `simulator/server/mqtt_publisher.py` · `libs/protocol/proto/rm27_base.proto` |

#### 比赛状态、发布和演示

- `simulator/server/state_manager.py` 的 `StateManager` 保存进程内的比赛数据。比赛阶段与时间、比分、两队经济、基地及前哨站血量、机器人数组和当前操作方各有字段。两队各有 1、3、4、5、6、7 六个可选编号，蓝方加 100。静态、动态数据按机器人 ID 分开保留。`select_robot` 与 `_sync_basic_robot_locked` 将当前车的等级、血量、热量等同全局数组对齐，切换操作方后能找回另一台车自己的数据。
- 查基础输入时，`set_base_game_status` 分别接收阶段、倒计时和已过时间。`set_basic_robot_values` 接收一行机器人的血量、热量及有符号的全局累计发弹量，手动设值不会触发旧版重生流程。`set_robot_static_status`、`set_robot_dynamic_status` 检查输入范围再写入。静态类型按 P-003 从当前编号取后两位，动态保留字段固定为零。机器人自己的剩余允许发弹量由动态表单独立提供。后勤累计经济字段发往网页时使用十进制字符串，保留超过 JavaScript 精确整数范围的数值。
- 同文件的状态更新线程负责比赛倒计时等周期演进。文件还保留双方角色状态、模拟判罚与复活、位置、事件队列、赛事演示写入入口和最多 100 条内存日志。`get_state` 在锁内整理各分组为网页、MQTT 发布器和可选 UDP 工具读取的数据。若网页 JSON 正确而桌面端的槽位错位，应接着看发布器如何挑选和排序数组。
- `simulator/server/mqtt_publisher.py` 的 `MQTTPublisher` 使用 Python Paho 连接 Broker，处理连接状态、订阅回调、定时发送、序列化和发布日志。三个循环分别从状态管理器取数。5 Hz 的 `_publish_loop_5hz` 发送 `GameStatus`。1 Hz 的 `_publish_loop_1hz` 发送 `RobotStaticStatus`、`GlobalUnitStatus`、`GlobalLogisticsStatus`。10 Hz 的 `_publish_loop_10hz` 发送 `RobotDynamicStatus`。这五项使用 `simulator/protocol/rm27_base_pb2.py`。对应的桌面端接收和解码分别见 `libs/transport/MqttDataSource.cpp` 和 `libs/protocol/BasicCodec.cpp`。
- 查发送数值时，`_publish_game_status` 组装局次、比分、阶段、计时、暂停与结算。`_publish_global_unit_status` 按当前阵营取己方、对方基地，而红蓝前哨站始终对应固定红蓝设施。机器人血量发送己方 1、3、4、7 号加对方同顺序八项。P-002 的己方累计发弹量取 1、2、3、4、6、7 六个槽位，编号 2 保留为零。`_publish_global_logistics_status` 选当前阵营的经济和等级。`_publish_robot_static_status`、`_publish_robot_dynamic_status` 读取选中机器人的状态。分清哪一方、哪个编号应看这些方法，输入界面的 12 行不会原样复制到每条报文。
- 发布器中其余不少 `publish_*` 和 `_on_message` 分支保留了旧版工具的事件、角色状态和上行指令，实现使用 `simulator/protocol/robomaster_pb2.py`。其中 `publish_radar_info_to_client` 在地图位置变动或演示帧触发时组装整组 `RadarInfoToClient`。基础周期循环、手工触发的消息、当前 Qt 客户端订阅清单可分别追到上面的循环、`simulator/server/app.py` 和 `libs/transport/MqttDataSource.cpp`。
- `simulator/server/match_simulation_engine.py` 的 `MatchSimulationEngine` 对应网页“一键赛事演示”。`control` 接收配置、启动、暂停、继续、停止和复位请求。`tick` 按单调时钟计算比赛进度和阶段，用固定种子与时间线生成可重复的位置、血量和事件，交给 `StateManager.apply_match_simulation_frame`。服务端按 10 Hz 调用它。启用了相应功能时还会发布旧版事件或雷达数据。进度、状态和最近事件返回网页。这份文件描述的是演示场景，五个基础主题的字段以 `libs/protocol/CONTRACT.md` 和 `libs/protocol/proto/rm27_base.proto` 为准。

**比赛时间由谁推进。** 手动模式下，`StateManager._update_loop` 每秒更新有倒计时的阶段，暂停时跳过推进。启动赛事演示后，`_match_simulation_clock_active` 让后台循环跳过阶段倒计时，改由演示引擎的 `tick` 和 `_apply_current_frame` 写入。后者还生成给网页的演示帧，`_collect_due_events` 记录已触发的事件。核对比赛时间时，应先确认当前由哪个时钟驱动。`simulator/server/state_manager.py` · `simulator/server/match_simulation_engine.py`

**当前状态和一次性事件怎么读。** 网页、HTTP 查询和基础消息发布器都用 `get_state()` 查看当前状态。旧工具读取待发事件时会调用 `get_events()`、`get_warning_events()` 或 `get_game_result_events()`，三个函数都会在锁内复制并清空对应队列。要核对操作后的数值，用 `get_state()`。要追结算事件何时产生、如何避免重复入队，从 `_enqueue_game_result` 入手。`simulator/server/state_manager.py` · `simulator/server/app.py`

#### 旧 UDP 工具与两路视频

- `simulator/server/protocol.py` 定义旧 UDP 工具用的 `CmdID`、`struct` 载荷布局和帧头函数。`pack_header` 准备带帧起始、长度、序号和校验位置的头，`pack_simple_header` 只写命令号与长度。这里与 `simulator/protocol/` 同名容易找错，后者存放的是 MQTT 使用的 Protobuf 定义和 Python 生成绑定。
- `simulator/server/crc.py` 保存 CRC8、CRC16 查找表以及计算、追加校验值的函数。`simulator/server/udp_receiver.py` 的 `UDPReceiver` 只在启用 `--enable-receiver` 时建立，线程接收旧 UDP 报文，检查帧头、长度和两级校验，识别机器人控制及地图交互消息并记录日志。
- `simulator/server/udp_sender.py` 的 `UDPSender` 只在启用 `--enable-udp-sender` 时启动。发送循环约每 0.1 秒读取比赛、单位、机器人状态和功率热量，取出待发结算、警告和事件，使用 `pack_simple_header` 发送无 CRC 的简化帧。普通位置发送方法虽保留，当前此循环并不调用。排查旧 UDP 时要先确定方向，接收端识别的是带校验格式，发送端构造的是简化格式。
- `simulator/server/config.json` 目前配置 `video_resource_path`，相对路径 `resources/videos` 以 `simulator/` 为起点。两套推流器都读这里。网页上传也写入普通图传组件所解析的目录。视频素材约定见 `simulator/resources/videos/README.md`，网页与 MQTT 地址参数见 `simulator/server/main.py`。
- `simulator/server/video_streamer.py` 的 `VideoStreamer` 负责普通图传。它扫描可用视频，选择输入文件，报告是否推流或暂停，管理 FFmpeg 进程和 UDP socket。`start()` 先启动等待线程。选片并调用 `start_streaming()` 后才转码。FFmpeg 输出 HEVC 字节流，分帧后由 `_send_frame` 切成带帧号、分片号和帧总长的 UDP 包，发往目标主机的 3334 端口。
- `simulator/server/hevc_annexb.py` 的 `HevcAnnexBFrameExtractor` 解决 FFmpeg 每次吐出的字节块和视频帧边界不一致的问题。`push` 暂存未读完的数据，识别 Annex-B 起始码和图像边界，返回组好的访问单元（近似一帧）。`flush` 取出尾部，`reset` 清空缓冲。服务端普通图传与独立 `simulator/tools/video_sender.py` 复用这段代码。
- `simulator/server/industrial_camera_streamer.py` 的 `IndustrialCameraStreamer` 是另一套遗留视频演示。它有独立的已选文件、播放状态、工作线程和 FFmpeg 进程，共用视频目录。代码探测能产生所需关键帧的 H.264 编码器，将 Annex-B 字节流切片并加循环包号，交 `MQTTPublisher.publish_custom_byte_block` 发到 `CustomByteBlock`。该视频载荷的解释属于旧模拟器的私有约定。当前桌面端的视频实现范围见 `libs/video/README.md`。

#### static

网页由 FastAPI 直接提供，入口是 `simulator/server/static/index.html`。无需前端打包流程，载入顺序为 Socket.IO、Vue、地图坐标工具、页面业务脚本。

- `simulator/server/static/index.html` 写页面结构、表单和事件绑定。顶部显示网页连接状态、阶段和当前操作机器人。基础区可编辑阶段与时间、两队机器人血量与热量、全局累计发弹量、当前机器人静态/动态状态、比分及经济。页面用标注区分了旧模块状态和后面的自动演示、地图、裁判操作、角色面板、视频及日志。数字输入由 `v-model` 与 JS 状态关联，`@change`、`@click` 等事件转交业务方法，基础输入错误显示在基础数据区域。
- `simulator/server/static/app.js` 检查本地依赖后把 Vue 挂到 `#app`。其 `data` 存储从服务端收到的比赛状态和用户正在编辑的草稿。`mounted` 注册 `connect`、`disconnect`、`update`、`simulation_status` 和 `simulation_frame`。更新函数区分正在编辑的字段和可被服务端刷新的显示值。`watch` 与 `computed` 管理表单状态、演示进度、队伍血量和筛选后的日志。换机器人时记录浏览器本地选择并发 `set_current_robot`。命令统一经 `sendCommand` 提交到 Socket.IO 的 `referee_command`，读取错误回执。演示控制单独发 `simulation_control`。文件也包含两张 Canvas 的绘制和拖动、视频操作及上传。
- `simulator/server/static/map_geometry.js` 导出 `MapGeometry.clientPointToCanvas`，将浏览器视口中的鼠标坐标换算为 Canvas 后备缓冲区像素。调整浏览器缩放、全屏或高 DPI 时，小地图拖动仍按实际画布宽高计算。小地图和路径编辑器的静态场地图是 `simulator/server/static/minimap_bg.png`，由 CSS 用作背景。
- `simulator/server/static/style.css` 管理控制台的卡片布局、红蓝阵营颜色、表单、地图、视频控制和日志样式。媒体查询负责窄屏重排、动画和减少动态效果。只调整位置或颜色，从对应 HTML 元素的 `class` 查这里。
- `simulator/server/static/vendor/vue.min.js` 是本地 Vue 2.7.14 浏览器库，负责模板绑定和界面刷新。`simulator/server/static/vendor/socket.io.min.js` 是本地 Socket.IO 4.5.4 浏览器库，负责网页与 Python 服务的事件连接。对应许可为 `simulator/server/static/vendor/LICENSE.vue-2.7.14.txt` 和 `simulator/server/static/vendor/LICENSE.socket.io-4.5.4.txt`。表单和事件的项目业务代码在 `simulator/server/static/app.js`。

##### 网页表单、视频面板与日志的取值位置

- **正在输入的数字如何保留。** 网页持续接收服务端快照。`mergeGlobalUnitStatusPreservingEdits` 保留正在编辑的行中血量、热量等列的草稿，其他行照常刷新。静态和动态详情表各有一个 `Dirty` 标志，通过 `isRobotStaticStatusFormEqual`、`isRobotDynamicStatusFormEqual` 比对服务端回显，一致后清除标志。阶段输入框只在第一份快照到达时用 `baseGameFormInitialized` 初始化，旁边的当前阶段仍随广播刷新。`simulator/server/static/app.js` · `simulator/server/static/index.html`
- **队伍血量进度条如何计算。** `getTeamRobotCards` 把界面上的编号映射到状态数组下标。`buildTeamHpSummary` 根据每队六台机器人的当前和最大血量计算单台及全队百分比。MQTT 的 `GlobalUnitStatus.robot_health` 由发布器另外选取双方各四项。两处数值对应的机器人集合可以在各自的函数中找到。`simulator/server/static/app.js` · `simulator/server/mqtt_publisher.py`
- **视频列表和计数从哪里来。** `uploadVideo` 用 HTTP 上传本地文件，服务端保存后广播新的 `videos` 列表。选择、暂停、继续等动作经 Socket.IO 交给相应推流器。普通图传面板的 `frame_id` 是帧号，工业相机状态的同名字段保存循环分片号，在模板中显示为 `packetId`。`simulator/server/app.py` · `simulator/server/static/index.html` · `simulator/server/video_streamer.py` · `simulator/server/industrial_camera_streamer.py`
- **网页日志与进程日志各记录什么。** `StateManager.log` 保留最近 100 条事件，网页从快照的 `logs` 取数据，用 `filteredLogs` 按类别筛选。发布器的 `_should_log_publish` 会跳过指定周期主题的打印，其他发布记录按条件输出到服务进程。通过启动脚本托管时，服务标准输出和错误输出写到 `simulator/.runtime/`，桌面 Qt 的 JSONL 则由客户端自己的日志类写入。`simulator/server/state_manager.py` · `simulator/server/static/app.js` · `simulator/server/mqtt_publisher.py` · `simulator/scripts/common.ps1` · `libs/diagnostics/JsonlLogger.cpp`

## CMakeLists.txt

`CMakeLists.txt` 是整个 C/C++ 构建的入口。它要求 CMake 至少 3.21，项目名 `RM27Client`，当前版本 `0.1.0`，设置 C++17、关闭编译器语言扩展、导出 `compile_commands.json`。对 MSVC 另加 UTF-8 编译选项。`AUTOMOC` 为 Qt 的信号、槽和属性生成元对象代码，`AUTORCC` 处理客户端的 `.qrc` 资源清单。

配置时先找 Qt 6.8 或更高的 Qt 6（Core、Network、Gui、Qml、Quick、QuickControls2），引入 Protobuf、Paho，再启用 CTest 支持。随后用 `add_subdirectory` 依次进入 domain、protocol、config、diagnostics、application、transport、presentation，最后进入 apps/client。子目录的 `add_library` / `qt_add_executable` 决定“编成哪个目标”，`target_link_libraries` 决定“这个目标依赖哪些库”。例如桌面程序链接 `rm27_transport`，传输库链接 `rm27_protocol`，协议库再链接 `protobuf::libprotobuf`。定位某个链接错误时顺着这条链找相应子目录的构建文件。`apps/client/CMakeLists.txt` · `libs/transport/CMakeLists.txt` · `libs/protocol/CMakeLists.txt`

## CMakePresets.json

`CMakePresets.json` 描述团队共用的构建方法。文件中有两类不同的条目。

| 配置预设（`configurePresets`） | 继承和实际设置 |
| --- | --- |
| `base` | 隐藏的公共基础，设 `generator` 为 `Ninja` 和输出目录 `${sourceDir}/build/${presetName}`。`sourceDir` 是根构建文件所在目录，`presetName` 取最终选中的配置预设名。Ninja 负责按构建规则调度编译命令。 |
| `windows-mingw` | 隐藏，继承 `base`，只在 Windows 主机上适用。根据环境变量设置 `CMAKE_PREFIX_PATH`（让 CMake 找 Qt）、`CMAKE_C_COMPILER`（gcc）、`CMAKE_CXX_COMPILER`（g++）和 `CMAKE_MAKE_PROGRAM`（ninja）。工具根目录和补充 PATH 的值见 `CMakeUserPresets.json`。 |
| `windows-mingw-debug`、`windows-mingw-release` | 分别继承 `windows-mingw`，把 `CMAKE_BUILD_TYPE` 定为 `Debug` 或 `Release`。二者是可选的公共配置，对应的本机预设 `local-*` 在它们之上补具体安装路径。 |

`buildPresets` 是构建预设。公共文件分别定义 `windows-mingw-debug`、`windows-mingw-release` 的构建入口，每项的 **`configurePreset`** 指向应使用的配置预设。配置名与构建名可以相同，它们分别由 `cmake --preset` 与 `cmake --build --preset` 选择。隐藏的 `base`、`windows-mingw` 只用作继承来源。项目构建什么目标仍由 `CMakeLists.txt` 决定。

## CMakeUserPresets.json

`CMakeUserPresets.json` 与公共预设同放根目录，CMake 读取预设时会将两份文件一起识别。文件中的 `local-debug` 和 `local-release` 各写了两次，分别是**配置条目**和**构建条目**。以下以点击“构建 Debug”为例。

```text
配置预设的继承（从公共设置到本机设置）
base
└─ windows-mingw
   ├─ windows-mingw-debug   → local-debug
   └─ windows-mingw-release → local-release

构建预设选构建目录（Debug）
buildPresets 中的 local-debug
    └─ configurePreset = local-debug
         └─ 对应的配置目录是 build/local-debug/
```

1. VS Code 按钮的 `task` 选中 `RM27: Build Debug`，任务执行 `scripts/build.ps1 -Configuration Debug`。脚本拼出 `local-debug`，自行从本机 JSON 的 `configurePresets` 中找同名条目，先检查四个绝对安装路径，再选用 `RM27_CMAKE_ROOT/bin/cmake.exe`。`.vscode/settings.json` · `.vscode/tasks.json` · `scripts/build.ps1`
2. 脚本执行 `cmake --preset local-debug`。这一步读**配置预设**，CMake 按 `inherits` 展开公共设置及本机环境，用 MinGW 的 gcc/g++ 检查编译环境，找到 Qt，配置依赖和工程目标，在 `build/local-debug/` 写入缓存和 Ninja 规则。`CMakeUserPresets.json` · `CMakePresets.json` · `CMakeLists.txt`
3. 随后执行 `cmake --build --preset local-debug --parallel <作业数>`。这一步读**构建预设**，`buildPresets` 中的 `configurePreset: "local-debug"` 把本次编译指到刚才的目录。Ninja 按规则执行所需的代码生成、编译和链接，生成 `build/local-debug/bin/RM27_Client.exe`。该本机构建条目直接指定自己的配置预设，继承关系发生在上一步的配置条目里。`CMakeUserPresets.json` · `build/`
4. 点击“运行 Debug / 模拟模式”会走 `run.ps1`，默认先重复上述配置和增量构建，然后用构建缓存定位运行时 DLL，传 `--config` 给程序。到这时，客户端读取的是业务 JSON。预设的作用已经在构建阶段完成。Release 对应另一套输出目录和缓存，而 `official`、`simulation`、`preview` 是独立的运行模式。`scripts/run.ps1` · `configs/`

本机两个配置条目都包含下面这些路径。移动 Qt 或换机器时，两条都要核对。

| 变量 | 当前文件中的值 | 谁读取、用来找什么 |
| --- | --- | --- |
| `RM27_CMAKE_ROOT` | `D:/Qt6/Tools/CMake_64` | PowerShell 脚本在其 `bin/` 找到要运行的 CMake。VS Code 扩展另读 `.vscode/settings.json` 中的 `cmake.cmakePath`。 |
| `RM27_QT_ROOT` | `D:/Qt6/6.11.2/mingw_64` | 公共预设用它设 Qt 包查找路径，脚本检查 `bin/Qt6Core.dll`。 |
| `RM27_MINGW_ROOT` | `D:/Qt6/Tools/mingw1310_64` | 提供 `bin/gcc.exe`、`bin/g++.exe`，和 Qt 安装包的 MinGW 工具链配套。 |
| `RM27_NINJA_ROOT` | `D:/Qt6/Tools/Ninja` | 提供 `ninja.exe`，供 CMake 调用构建工具。 |

本机 `environment.PATH` 把 Qt 的 bin、MinGW 的 bin、Ninja 目录放到本次工具搜索路径前面，通过 `$penv{PATH}` 保留父进程原有的 PATH。公共文件使用 `$env{RM27_QT_ROOT}` 等读取选定预设的环境。只想看看 CMake 能识别哪些公开条目，可在根目录用同一份 CMake 运行 `cmake --list-presets=all`。当前本机列出的配置预设、构建预设各有四个：两种 `local-*` 和两种 `windows-mingw-*`。`CMakePresets.json` · `CMakeUserPresets.json`

## CMakeUserPresets.json.example

`CMakeUserPresets.json.example` 随仓库提供。新工作区缺少本机文件时，在项目根目录将它复制为 `CMakeUserPresets.json`，按本机安装位置修改 Debug 和 Release 的四个根路径。模板中的 `.example` 文件名用于分发示例，CMake 实际识别的是去掉该后缀的文件。项目的构建脚本要求本机条目中直接写明这四项绝对路径。修改所有人共用的构建方法看 `CMakePresets.json`，修改单机工具路径看 `CMakeUserPresets.json`，修改业务运行参数看 `configs/`。

## .editorconfig、.gitignore 与 .git

- `.editorconfig` 给编辑器规定 UTF-8、LF、文件末尾换行和默认 4 空格缩进，JSON 和 QML 特别设为 2 空格。
- `.gitignore` 排除根构建目录、个人预设、`configs/local*.json`、日志、临时文件及本地文档等路径。本篇 `docs/代码结构.md` 在现有忽略范围内，普通 `git status` 不会列出它。可直接从工作区打开。已在 Git 中跟踪的规则 PDF 仍可在仓库里找到。
- `.git/` 是 Git 的对象、提交引用、索引及仓库配置，由版本控制工具维护。项目源码位于它的同级目录。
