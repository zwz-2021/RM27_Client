## 1. 原版技术依赖说明（不是新版步骤编号）

当前项目完成了可构建的客户端骨架，以及从 RM26 移植的独立模拟器。客户端尚未接入比赛数据，也没有连接这个模拟器。

下图保留原版的技术依赖说明，仅供查阅；实际任务以通俗版的六步和用户指定范围为准：

```text
2027 契约、依赖与验证样本
    ↓
Protobuf 编解码 + RM27 最小模拟器
    ↓
真实 MQTT 收发与会话生命周期
    ↓
统一比赛状态、数据有效性与坐标模型
    ↓
命令用例、输入控制、角色与阶段限制
    ↓
UDP 图传收包、组帧、解码
    ↓
故障恢复与底层联合验收
    ↓
展示模型
    ↓
正式 QML 工作台与交互打磨
    ↓
发行包、官方接口与现场验收
```

图传可以在 MQTT 接入后，与状态和命令开发并行，但必须在正式工作台开发前完成独立验收。全程可以使用现有诊断页、命令行工具和最小视频测试窗口；这些只服务于验证，不提前铺开正式 UI。

首个可用闭环以“一个步兵操作端的状态、基本控制、兑换/复活和图传”为基线，随后完成指挥手/哨兵、重装、飞镖。基础类型从一开始支持 RM27 身份与能力差异。具体角色优先级可按队伍实际使用情况调整，不改变底层依赖顺序。首个步兵底层闭环通过后即可完成对应展示模型和 UI；后续角色各自重复相同顺序，无需等所有角色底层全部实现。

### 2.1 决定架构的协议要求

- 赛事数据：MQTT 直接承载 Protobuf v3 二进制，topic 为指令名；文档要求 Protobuf 3.15 以上。官方服务地址 `192.168.12.1:3333`，自定义终端地址 `192.168.12.2`，MQTT client ID 使用所连机器人的 ID。见通信协议 PDF 第 47 页（46）。开发环境使用可配置的本地地址，不自动修改操作系统网卡设置。
- 指令概览共有 32 种消息，最高 QoS 为 1；消息有各自的方向和频率。`GameStatus` 5 Hz，`RobotDynamicStatus` 10 Hz；`KeyboardMouseControl`、`CustomControl` 最高 75 Hz；部分业务指令最高 10 Hz。见 PDF 第 47-51 页（46-50）。不要将示例代码中的默认 QoS 2 当作要求。
- 视频：UDP 3334、H.265/HEVC、1920×1080、60 帧，无重传；包头为大端的 2 字节帧号、2 字节分片号、4 字节整帧字节数。每包含头最多 1400 字节，数据最多 1392 字节。见 PDF 第 47 页（46）。
- 地图指令：`MapClickCmd` 上行，`MapClickInfo` 下行；云台手发送间隔至少 0.5 秒，半自动机器人对应操作手至少 3 秒。见第 2 章概览及第 1.3.1 节，PDF 第 34-35 页（33-34）。具体操作身份与 client ID 的对应关系还需接口测试核实。
- `CustomControl.data` 上行最多 60 字节；`CustomByteBlock.data` 下行最多 300 字节。自定义业务封包仅在另有明确需求和约定时实现，不把旧模拟器的工业相机封包当成赛事标准。

**客户端的首要任务是 MQTT/Protobuf 和 UDP 视频。** 第 1 章的串口 A5 帧、CRC、雷达无线解析、机器人间 0x0301 绘图并不是本客户端默认要直接实现的接入链路；只有确定需要额外桥接时再增加相应适配器。

### 2.2 决定业务模型的规则要求

1. RMUC 上场兵种已变化：重装 1、步兵 3/4、哨兵 7，另有空中系统 6、飞镖 8、雷达 9。比赛规则 PDF 第 21-29 页（20-28）。协议附录仍保留部分通用编号，包括步兵 5，因此应区分“合法协议 ID”与“本赛项当前阵容”，不能沿用 RM26 英雄/工程/三步兵阵容，也不要简单拒绝所有预留或未知值。
2. R/B 前哨是按开局场地命名的固定实体，不随己敌视角或控制权变化改名；己方/敌方、红方/蓝方、固定 R/B 是三种不同概念。通信协议 PDF 第 80-81 页（79-80）。
3. 比赛状态需要包含基地/前哨、阵地的临时或完全控制、累计控制度、经济、机器人状态和关键事件，而不只是血量。客户端消费赛事权威结果，不独立重判胜负。
4. 操作资格随阶段、角色和机器人状态变化。例如五秒倒计时不响应机器人控制；步兵性能体系选定后赛中不可更换；复活、远程回血和远程补弹有前置条件及延迟。见比赛规则 PDF 第 74-78、92、122 页（73-77、91、121）。客户端可做校验和提示，成功与否以权威同步/明确结果为准。
5. 显示与控制限制需分开表达：超热时图传断开但地图和自定义 UI 可用；飞镖命中、黄牌对应的影响范围又不同，且飞镖遮挡期间终端仍可收到图传。见比赛规则 PDF 第 68、112、125 页（67、111、124）。接收状态不能等同于允许展示或操作的状态；具体自定义终端应如何配合、完整限制状态从何处获取，须列入官方接口确认，不根据热量或事件自行猜测全部限制。
6. 使用前须接入官方赛事数据接口测试，终端不得用无线收发。见制作规范 S49/S50，PDF 第 19 页（18）。发行验收还应考虑场内有线网络、离线运行、操作设备接口和不得与操作间外通信等约束。软件不代替硬件检录。

### 3.3 本次验证的边界

- 当前源码 Debug 配置与构建通过。构建出现 Qt6TaskTree 间接依赖和 VulkanHeaders 的非阻塞告警，未导致本次失败；后续部署再核查其实际影响。
- 模拟器入口 `--check` 通过，11 项 Protobuf 生成/运行时工具测试通过。它们验证现有生成代码和工具，并不证明符合 RM27。
- 未执行客户端真实 MQTT 端到端联调、官方设备接入或真实视频解码验证；当前检查环境未发现 PATH 中的 FFmpeg。
- 本机 Qt kit 未发现 Qt6Mqtt 包，不能直接假定 `Qt6::Mqtt` 已可链接。通信实现前需先完成 MQTT 库与现有 MinGW 工具链的集成小样。

## 4. 原版技术分组与检查事项（编号不对应新版六步）

以下“阶段 0-9”是历史技术分组，不是另一套待执行任务。Codex 应只提取当前通俗版步骤需要的检查事项。

### 阶段 0：冻结可追溯的契约与依赖

**任务**

- 建立 32 种消息的清单：topic、方向、字段号/类型/单位/枚举/数组顺序、频率、最高 QoS、适用角色、PDF 来源、确认状态。
- 分开定义运行环境与数据来源，避免 simulation 同时表示内置心跳和外部 MQTT 模拟器。保留 Mock 作为独立开发来源；网络模拟器与官方环境共用正式通信实现、使用不同配置。
- 优先验证 MQTT 库、Protobuf C++ 和 UDP 所需 Qt Network 能否用当前 Qt/MinGW 构建并部署。登记 HEVC 解码依赖方案，其集成验证可延后到阶段 5 开始前。固定生成器和运行库版本，避免混用其他编译器产物。
- 确定 schema 的唯一维护位置、C++/Python 生成规则和许可证归属，生成文件不手工修改。RM26 如需保留则明确隔离版本，不静默兼容混用；P-001、P-002 按用户指定范围参考旧实现，不能据此引入其他旧版消息定义。
- 建立少量独立核对的固定报文样本和预期字段值；列出本文件第 6 节中的待确认项。

**交付与通过条件**：可以从干净构建目录编译 MQTT/Protobuf 依赖小样；消息清单有来源；不明确字段标为待确认而非擅自补成“官方定义”。HEVC 工具链不阻塞本阶段，无需完成正式界面。

### 阶段 1：实现 protocol，并建立 RM27 最小验证器

**落点**：`libs/protocol/`、必要的协议测试、`simulator/protocol/` 与最小场景。

**任务**

- 新增 `rm27_protocol` target，封装 topic 路由、Protobuf 编解码、长度/类型/范围检查；不依赖 QML，不包含网络连接和业务裁判逻辑。
- 第一批实现 GameStatus、GlobalUnitStatus、GlobalLogisticsStatus、RobotStaticStatus、RobotDynamicStatus、RobotRespawnStatus，然后按第 5 节扩展。完整列清单不等于一次性写完所有角色业务。
- 保留 optional 的存在性，区分“字段缺失”和“显式为 0/false”；对未知枚举保留原值/明确未知态。按每条消息契约决定缺字段的更新行为，不把所有消息一概当作全量或增量。
- 模拟器先对齐这批消息、机器人身份、5/10/1 Hz 调度，以及至少一个命令→状态变化场景；地图、重装等随后逐组升级。
- 为零值、缺字段、未知字段、截断负载、非法数组和错误 topic 建立必要测试。检查空 Protobuf 在语法上可能有效，但是否足以更新业务状态由适配层判断。

**交付与通过条件**：无需 GUI 和 Broker 即能运行编解码验证；C++/Python 互通；同时以人工核对样本或官方报文校验，避免两端共享错误 schema 仍互相通过。尚无处理方案的歧义消息可先隔离；P-001、P-002 按用户记录的指定依据开发，完成后分别记录互通结果与官方接口未验证状态。

### 阶段 2：真实 MQTT 通信与会话生命周期

**落点**：`libs/transport/`、`libs/config/`、`libs/application/`、组合根和 diagnostics。

**任务**

- 实现真实网络数据源和发布入口，支持 Broker、机器人 client ID、超时、连接配置及明确错误输出；topic 与频率来自契约，不由 QML 拼接。
- 实现连接、订阅确认、收包、断开、重连后重新订阅、停止与退出。用会话代号/取消机制隔离旧连接回调，不能只靠当前 active 布尔值。
- 区分“Broker 已连上”“订阅已就绪”“某消息已收到”“数据仍新鲜”；MQTT 与视频健康分别维护。
- 回调先交付有界数据，避免解析/日志/业务长时间占用网络回调。QObject 状态统一回到所属线程；在有实际需要的模块内部引入 worker。
- 从此阶段加入轻量录包：接收时间、会话、topic、原始负载、协议版本。高频录制单独有界缓冲，不直接对每个包使用当前逐条 flush 的状态日志路径。

**交付与通过条件**：现有诊断页或工具能显示外部模拟器真实报文计数/字段；停止 Broker 能明确降级，恢复后重新订阅；重复启停和退出不遗留连接；旧连接数据不会覆盖新会话。此阶段不要求正式比赛工作台。

### 阶段 3：领域状态、数据有效性与地图计算

**落点**：`libs/domain/`、`libs/application/`。

**任务**

- 建立 MatchState、RobotState、LogisticsState、BattlefieldState、MapState 等明确类型，按真实职责拆分更新器，不扩张为一个巨大 ClientSession。
- 由协议适配层将 DTO 转成领域更新；维护唯一权威状态。各 topic 只更新自己负责的字段/实体，保留数据来源、接收时间、有效性和会话归属。
- 机器人身份、操作端角色、控制来源、控制模式和可操作能力分开建模；未知/未上场/战亡/掉线/数据过期不共用“0 血量”表达。
- 建立固定 R/B 实体、红蓝身份、己敌视角转换。世界坐标内部统一单位；米、厘米、分米在边界转换。场地尺寸、地图显示变换、点击逆变换不写在 QML 业务表达式里。
- 建立坐标来源、未知/越界/过期处理、雷达特殊标识和路径解码；MQTT 路径按第 2.2.16 节相对起始点的定义实现，串口路径按其自身章节处理。真正无法确定的部分单独记录并隔离。
- 处理跨局、身份切换、重连和暂停。倒计时可按单调时钟做显示插值，但定期被权威时间校正；不得本地提前判局结束。
- 为限制状态预留原因、范围、到期时间和可用动作，不因“收到视频”就默认可以展示所有信息。协议不足以明确表达时，保留待确认状态和诊断记录。

**交付与通过条件**：离线固定消息序列可还原确定状态；乱序 topic 到达不清空其他数据；0 和未知可区分；红蓝视角切换不交换 R/B 实体；断线数据变为过期；新一局不残留上一局的 Buff、命令或路径。

### 阶段 4：命令用例与键鼠控制

**落点**：`libs/application/` 的用例/命令接口、`libs/protocol/`、transport 发布适配器；输入采集靠近应用窗口边界。

**任务**

- 建立“用户意图 → 角色/阶段/状态校验 → 参数校验 → 限频 → 编码 → 发布 → 反馈”的统一入口。UI 使用具体动作，不传原始 topic 或任意字节参数。
- 第一批完成性能选择、兑换弹量、复活；随后做 MapClickCmd/哨兵操作，再做重装装配、能量机关与飞镖。
- 校验 17mm 普通兑换的 10 发倍数、接收者 ID 与固定 7 字节列表、合法图标、各类命令的频率。地图至少 0.5 秒/3 秒的限制按角色和当前控制方式分别执行，不套用统一 10 Hz。
- 支持未提交、已提交待同步、已确认、明确失败、超时未确认等状态。MQTT PUBACK 只说明传输层确认；SentryCtrlResult 才是该命令的明确业务结果。其他命令通过适用的权威同步观察，无法唯一关联时诚实标为“待确认/结果未知”。
- 防止连续点击、网络重连和 QoS 重复造成重复业务提交；兑换、复活、发射等不因断线自动重放。不能虚构协议中不存在的请求序号来保证服务端幂等。
- KeyboardMouseControl 按协议位掩码和频率生成；输入采集、控制源选择和发送调度分离。窗口失焦、弹窗切换、停止/断线时清理按键和鼠标状态；恢复后不继续发送旧按下状态。仅在已选择自定义终端为控制源时启用相应控制流程。
- CustomControl 按当前文档实现受限的字节通道；具体机器人私有业务、版本和单位仅在另有明确需求和约定时加入，不得冒充官方消息定义。

**交付与通过条件**：无正式按钮也能通过测试驱动完成“请求 → 模拟器处理 → 权威同步/结果”；非法阶段、参数和超频会被拒绝并说明原因；发送成功不会立刻改成本地已复活/已到账；断线重连不会补发旧消费指令。

### 阶段 5：UDP 图传基础链路

**落点**：`libs/video/`，必要的 UDP 接入可复用 transport 基础设施。

**任务**

- 在模拟器修正 1400 字节上限并准备已知 H.265 测试码流；本阶段按当前协议实现标准图传，不把旧模拟器的私有工业相机封包纳入标准图传。
- 分离 UDP 收包、头校验、分片组帧、HEVC 解码和帧交付；测试中先落完整帧/输出统计，再接最小 Qt Quick 显示面。
- 校验大端头、包长、整帧大小、分片位置和一致性；设置单帧、在途帧数、等待时长和总内存上限。处理重复、乱序、缺片、帧号 16 位回绕和停止后的迟到数据。
- 无重传时丢弃不能恢复的残帧；解码错误后按实际码流重同步，等待可解码关键帧。分片编号起点、码流封装与恢复行为通过真实设备样本确认。
- 明确解码 worker、帧缓冲所有权和退出顺序。帧队列有界，落后时优先追上实时画面，避免越播越慢；先保证可稳定的软件解码路径，再评估硬件加速。
- 输出包速率、残帧/解码错误、帧率、最近一帧时间和处理时延；没有发送端时间戳时，不把本地处理时延称为端到端图传延迟。

**交付与通过条件**：已知 1080p60 测试源可持续解码显示；缺包/乱序时丢帧和恢复可观察；MQTT/键鼠不被视频阻塞；断流状态明确，停止和退出能回收资源。实际设备性能不足时先记录瓶颈，再确定优化目标。

### 阶段 6：底层联合验收与故障恢复

**任务**

- 组合 MQTT 状态、命令、键鼠和视频，运行至少一轮完整比赛阶段序列；建议再做 30 分钟连续负载检查，时长是工程建议而非赛事条文。
- 覆盖断开/恢复 Broker、视频单独断流、消息静默、异常负载、旧会话迟到回调、角色切换、跨局、磁盘写入失败与退出。
- 验证一条链路异常不会导致其他链路阻塞或错误宣告全部健康；控制指令不补发；日志能复现问题。
- 补齐当前阶段实际需要的 RM27 场景。完整物理/经济仿真、对战 AI 和用户回放界面不作为进入 UI 阶段的条件。

**交付与通过条件**：给出可重复场景、预期结果和实际统计；无无限增长队列、明显内存累积、退出卡死和跨会话状态污染。可靠性要求从前面各阶段执行，此阶段是联合检查，不是第一次补异常处理。

### 阶段 7：展示模型

**落点**：`libs/presentation/`。

**任务**

- 按比赛总览、当前机器人、地图、事件/告警、角色操作组织模型，按需拆分 ViewModel 与列表模型。
- 提供数值、单位、未知/过期态、操作可用性及原因、命令进度、显示限制与链路健康属性；不暴露 Protobuf 对象给 QML。
- 控制通知频率和批量更新；视频帧走专用通道，避免每帧重建整份比赛快照。
- 将现有启动/停止和运行信息能力接到正式会话，保留诊断能力。

**交付与通过条件**：固定场景驱动模型时属性和动作正确；换简单测试页面仍可使用全部业务；QML 无需理解 topic、协议字段号、价格公式或身份权限。

### 阶段 8：正式 UI 与角色工作台

**落点**：`apps/client/qml/` 和必要的输入/视频显示适配组件。

**顺序**

1. 连接/身份配置与赛前自检，确保进入的操作端身份清楚。
2. 步兵最小工作台：图传、血量/热量/弹量/经济、阶段与时间、兑换/复活反馈、异常提示。
3. 地图与指挥手/哨兵工作台：机器人、路径、阵地控制度、标记、哨兵状态与操作反馈。
4. 重装工作台：装配难度、科技核心步骤、剩余时间、确认/取消与结果。
5. 飞镖工作台：目标、闸门状态、确认发射与限制反馈；其他功能按当前协议和队伍实际需求加入。
6. 统一视觉、布局、1080p与窗口缩放、快捷键、焦点、操作效率和各种限制/断流场景；依据制作规范 S42，PDF 第 17 页（16），检查终端软件/UI不展示赞助商品牌元素。

**交付与通过条件**：所有显示绑定已经验证的状态模型，所有动作走已有用例；协议数据缺失时不伪造正常值；操作手能看出当前身份、可用动作、请求结果及故障原因。UI 对限制机制的处理以已确认规则和接口行为为准。

本阶段按角色分批交付。步骤 2 可在步兵对应的阶段 0-7 验收后进行；步骤 3-5 各自先补齐对应下层能力再接 UI，避免一次性开发全部角色导致首个可用版本迟迟不能交付。

- 生成 Release 发行包，收集 Qt 插件/QML、通信与解码运行库、默认配置和必要许可证；清除开发机绝对路径依赖。

- 验证有线网卡选择、官方地址/身份、视频、输入源选择、命令频率、各角色权限以及界面限制的实际表现。

- 保存现场可用的上一稳定版本、配置导入方式和本地日志定位说明。完整回放、复杂皮肤可在稳定基线之后开发；机器人私有业务仅在另有明确需求和约定时，通过当前协议允许的通道实现。

## 6. 必须保留的协议疑问

下面保留原核对中的问题及待验证事项，持续状态以 [规则与协议问题记录](development-gaps.md) 为准。原文无法确定且没有用户处理说明的部分先隔离；已有说明的按其范围执行，其他明确功能可以继续。不把现场未验证或不同接口的正常差异一概当作协议冲突，也不等待文档更新才推进开发。

1. **RadarInfoToClient 的 schema 有原文问题（P-001）。** 通信协议 PDF 第 68-69 页（67-68）的表格与示例不一致，示例 `repeated uint32 RadarSingleRobotInfo;` 缺少字段号，且与后续子消息结构不符，直接交给 protoc 无法编译。已渲染核对原页，确认不是提取文本损坏。用户现已明确按模拟器实际发送的雷达协议设计接收，也可参考 `RM26_Client`；官方补充后再修改雷达部分。不再将这项保持隔离作为开发要求，原文疑问与官方未验证状态仍保留。
2. **路径应按接口各自定义实现。** 第 2.2.16 节 MQTT 路径描述为相对起始点；第 1.3.2 节串口路径描述为相对前一点。两者属于不同接口，应按各自章节实现，不默认使用同一算法。只有具体实现仍无法按对应原文确定时，再记录具体问题。
3. **robot_bullets 的长度与顺序未充分说明（P-002）。** 第 2.2.4 节明确了 robot_health 的 8 项顺序，但弹量只写“己方机器人剩余累计发弹量”。用户说明此项 26/27 赛季协议内容一致，已指定按模拟器发送的对应协议设计接收，也可参考 `RM26_Client`。后续实现时读取对应源码确定具体映射；当前仅记录用户方案，没有新增原文核验、代码或测试。
4. **身份与角色映射需确认。** MQTT client ID 要求所连机器人 ID，但指挥手、哨兵控制源、多终端及切换权限不能只从客户端自行选一个数字推定。
5. **限制机制的通知和终端行为需确认。** 当前消息清单没有完整、明确的统一遮挡状态消息。PenaltyInfo/Event 等如何涵盖飞镖命中次数、累计时长和所有限制范围，及官方已执行哪些处理，需实际核查；不得把事件触发时间等同于限制权威起始时间。
6. **视频设备边界需确认。** 头和包长已有明确规范；分片编号起点、丢包后的实际码流恢复、码流封装及关键帧情况需官方样本验证。仅与当前模拟器一致不足以认定兼容。

## 7. 历史任务拆分示例（当前任务以通俗版为准）

下面保留旧版的拆分示例，不指示下一轮立即执行。当前任务由通俗版开发路线、实际代码和用户的最新要求确定：

1. 新建消息契约表和疑问清单，冻结网络配置/身份约定，验证 MQTT 与 Protobuf 在现有 MinGW 下的依赖小样。
2. 建立 `rm27_protocol` 和正式 schema 的生成规则，先落地六类基础状态消息及独立固定样本。
3. 将模拟器对应消息、阵容和发送频率改到 RM27，形成最小准确基准；不用先迁移全部旧 Web 面板。
4. 实现真实 MQTT 适配器及显式网络模拟配置，通过现有诊断入口收到真实 GameStatus/RobotDynamicStatus。
5. 建立统一状态聚合和首个通用命令闭环，再按上述路线推进输入、视频、角色能力和最终 UI。

不先扩展正式 QML 页面，也不先复制 RM26 全量业务。每次新增界面前，先确认它依赖的状态、动作、异常路径已经在下层可验证。
