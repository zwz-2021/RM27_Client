## RobotStaticStatus 的 14 个字段

两版示例中以下字段的名称、编号、类型、`optional` 标记完全相同；表格对字段的基础含义也相同。对提取文本规范化后逐项比较，均为 14 个匹配声明；同时检查了原页，排除了换行和空格造成的提取误差。

| 编号 | 字段名 | 类型（两版均 optional） | 两版基础含义 |

| 1 | `connection_state` | uint32 | 连接状态：0 未连接，1 已连接 |
| 2 | `field_state` | uint32 | 上场状态：0 已上场，1 未上场 |
| 3 | `alive_state` | uint32 | 存活状态：0 未知，1 存活，2 战亡 |
| 4 | `robot_id` | uint32 | 机器人编号 |

| 10 | `max_heat` | uint32 | 最大热量 |

两版原文均未给 `robot_type` 数字编码表。附录二的标题和正文明确说明的是机器人 **ID**；不能把它直接当作第 5 字段的官方枚举。P-003 本次采用的类型语义来自用户明确指定的旧项目实现迁移，官方编码表缺失的事实仍应保留。

字段结构一致不表示所有性能选项一致。2026 第 58–59 页列出：

| 性能体系 | 两版共同选项 | 仅 2026 列出的选项 |
| --- | --- | --- |
| 发射机构 | 1 冷却优先，2 爆发优先 | 3 英雄近战优先，4 英雄远程优先 |
| 底盘 | 1 血量优先，2 功率优先 | 3 英雄近战优先，4 英雄远程优先 |

2027 第 61 页只列共同的 1、2。本次类型迁移不能恢复旧赛季的 3、4 性能业务；收到其他原始数值也不能擅自改写成某个已知选项。

## 旧项目实际数据流

以下行号均为本次读取的同级 `RM26_Client` 文件中的一基行号。

1. **模拟器生成默认值。** `sim/server/state_manager.py:306` 的 `_create_robot_static_status_state()` 将 `robot_type` 设为 `current_robot_id % 100`；第 1319–1322 行的状态设置方法在未显式给值时也采用该约定。
2. **切换当前机器人。** `sim/server/main.py:708` 把 `static_status["robot_type"]` 更新为新 `robot_id % 100`，随后交给状态设置方法。
3. **发布真实字段。** `sim/server/mqtt_publisher.py:1195` 的 `_publish_robot_static_status()` 建立消息；第 1204 行填写 `robot_id`，第 1205 行直接将状态中的 `robot_type` 写入消息，缺省时使用 `robot_id % 100`。
4. **客户端解释。** `src/core/GameData.cpp:34` 的 `robotTypeFromProtocolId(robotId, fallbackType)` 先按 `robot_id % 100` 识别 1–7，无法匹配时再按 `robot_type` 的 1–9 识别。第 1979 行的 `updateRobotStaticStatus()` 在第 1982 行调用该函数，并把得到的角色用于机器人状态。

该实现说明了指定基准的实际约定：Static 类型值按身份编号的个位组区分角色，包括 3、4、5 三个步兵编号，而不是把所有步兵都写成 3。旧函数最后把无法识别的类型默认当作步兵 3，这是旧代码的兜底行为；本次不沿用，未知值保留为未知，避免误认机器人。

## 旧项目中两套类型枚举不能混用

| 来源和用途 | 旧数值定义 | 与本次 Static 字段的关系 |
| --- | --- | --- |
| `src/network/proto/robomaster.proto:31` 的 `enum RobotType`，被第 84 行 `RobotStatus.type` 引用 | 0 未知，1 英雄，2 工程，3 步兵，4 空中，5 哨兵，6 飞镖，7 雷达 | 这是另一条 `RobotStatus` 消息的枚举，不能复制到 `RobotStaticStatus.robot_type` |
| 同文件第 428 行 `RobotStaticStatus.robot_type` | 声明为 `uint32`，没有引用上述 proto 枚举 | 实际数值来源是上节模拟器状态与发布代码 |
| `src/network/Protocol.h:50–60` 的内部 `enum class RobotType`，配合 Static 接收函数 | 1 英雄，2 工程，3 步兵 3，4 步兵 4，5 步兵 5，6 空中，7 哨兵，8 飞镖，9 雷达 | 与旧 Static 接收函数及模拟器默认值相对应，是本次用户指定迁移的实现依据 |

例如 Static 的旧约定 `robot_type=6` 表示空中，而另一个 proto 枚举的 6 表示飞镖。只看枚举名称相同就复制，会产生实际错配。

## 本次用户约定的迁移边界

结合用户说明、旧数据流及 2027 附录：旧类型值 1 对应的角色迁移为重装，2 对应保留位；3、4、5 为对应步兵，6 为空中系统，7 为哨兵，8 为飞镖，9 为雷达。红蓝身份仍由 `robot_id` 区分，不能用单独的类型值推定阵营。

旧 Static 接收函数及其内部枚举没有给原始类型值 10、11 的语义，因此本次仍保留为未知原值；其他未列明数值也保持未知。**`robot_id=10/110` 仍可按官方附录识别为基地，`robot_id=11/111` 仍可识别为 R/B 前哨，这不等于 `robot_type=10/11` 已获定义。**

缺失 optional 字段、显式的 0、已知类型和未知原值分别保留。角色解释采用已知 ID 优先、类型值后备的策略；已知 ID 与类型不一致时，原始类型仍保留，离线诊断可以同时查看原始字段和解释角色。该优先策略来自指定旧实现的处理方式，不表示不一致的报文已经符合官方协议。

本次程序修改及对应检查已完成，实际结果见 [问题记录的实施与验证结果](development-gaps.md#实施与验证结果2026-11-01) 和开发路线文末。旧项目约定迁移和离线检查不能证明官方编码表已经补全，也不能代替官方设备验证。
