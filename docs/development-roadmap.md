# RM27 Client 开发路线：照着和 Codex 一步步做

更新日期：2026-10-30。本次更新的是开发说明，尚未实现新的通信或界面功能。

你不需要先学会设计软件架构。你主要负责确定想要的功能和界面、观察运行结果，以及准备实车测试条件；查协议、选用软件库、修改代码和运行程序检查，由 Codex 负责。

## 一、先看懂这条路线

你理解的大方向是对的。这里稍微调整一下顺序：先按 2027 协议统一第一批数据，通信跑通后逐组增加功能，最后完善正式界面并接实车。

| 步骤 | 做什么 | 你会看到的结果 |
| --- | --- | --- |
| 1 | 按 2027 协议准备基础数据，同时更新模拟器对应的网页输入项 | 模拟器网页能设置要测试的比赛时间、血量等数据 |
| 2 | 完成 MQTT 数据接收和指令发送 | 网页改血量，客户端跟着变；客户端发指令后显示模拟器处理后的状态 |
| 3 | 完成 UDP 图传接收和播放 | 模拟器发测试视频，客户端能连续播放 |
| 4 | 分批补齐比赛功能，每批同时更新客户端、模拟器和模拟器网页 | 兑换、复活、地图、哨兵、重装、飞镖等所需功能逐个可用 |
| 5 | 用模拟器完整测试，再完善正式 UI | 能从准备阶段跑到比赛结束，界面布局和操作也符合需求 |
| 6 | 打包到目标电脑，完成实车和官方接口测试 | 脱离开发环境能运行，真实设备的数据、视频和操作经过验证 |

这里的“自底向上”就是：**先保证数据能收到、指令能发出、结果正确，再把这些功能放进正式界面。**

通信阶段可以有简单的测试页面，用来看数字、点测试按钮、播放视频。它可以不好看，但必须能帮助你判断功能有没有工作。正式 UI 的布局、配色和操作细节放在第 5 步完善。

### 只需要认识的几个词

| 词 | 在这个项目里是什么意思 |
| --- | --- |
| 客户端 | 你正在开发的操作软件，最终给操作手使用 |
| 模拟器 | 暂时代替真实比赛设备，给客户端发送测试数据、接收测试指令的程序 |
| 模拟器网页 | 你用浏览器打开的控制台，用来改血量、时间等测试数据 |
| 通信协议 | 双方约定“发什么数据、每个数字代表什么、多久发一次”的说明书 |
| MQTT | 在本项目中，用来传比赛数据和操作指令 |
| UDP | 在标准图传这条线路中，由模拟器或真实设备发送视频，客户端接收视频 |
| 联调 | 把双方程序接起来，检查一边操作后，另一边是否收到并正确响应 |
| UI | 你能看到和操作的界面 |

因此，第 3 步的目标是“模拟器发送视频，客户端接收并播放”。如果以后有明确的额外用途，再增加客户端的 UDP 发送功能。

## 二、现在做到哪里了

按当前源码核对，起点是：

- 客户端已经能打开，能显示简单状态，也有构建和运行脚本。
- 当前的“模拟模式”是客户端自己生成演示数字，还没有连接 Python 模拟器。
- Python 模拟器及其网页已经存在，但程序中仍有 2026 年的协议和功能，需要逐项更新。
- 客户端真正的 MQTT 收发、UDP 图传和正式比赛界面都还没有完成。

**本文件的六步是待完成的计划，不表示程序已经具备这些功能。** 后续让 Codex 以实际代码和运行结果为准更新进度。

## 三、你和 Codex 怎么配合

每次选下面一个步骤；第 4 步则每次只选一组功能。把对应指令复制到聊天里，Codex 就应该实际修改和检查项目。

你不必替 Codex 选择软件库、类名或代码放置方式。只有涉及你真正的偏好或条件，例如先支持哪种机器人、界面长什么样、实车什么时候可用，才需要你决定。

新开聊天继续本项目时，可以先复制这段：

```text
请先阅读 docs/development-roadmap.md，并检查当前实际代码和进度。
我没有自定义客户端开发经验，请用普通话说明这次要做什么。
请实际完成我指定的小任务，技术实现和必要的程序检查由你负责。
能由你运行的检查请先运行，需要我观察界面或连接设备时，再给我简短步骤。
完成后告诉我：做了什么、怎么启动、应该看到什么、哪些已验证、哪些还没验证。
请更新本文件末尾的进度记录，不要只写“已完成”。不要提前开始其他阶段。
```

下面每条阶段指令都按这个约定执行。文中的文件路径是项目内的位置，Codex 能自己找到，你不用手动打开所有文件。

## 四、按这六步开发

### 第 1 步：先让双方对基础数据有相同理解

**这一步做什么**

先处理比赛阶段、剩余时间、机器人编号、血量、热量、允许发弹量和经济。Codex 对照项目里的 2027 协议更新双方程序，并让模拟器网页能设置这些数据。其余复杂功能留到第 4 步。

**可以直接发给 Codex**

```text
请按开发路线完成第 1 步：按 docs/rules 下的 2027 通信协议，
统一客户端和模拟器要使用的第一批基础数据，包括比赛阶段、时间、
机器人编号、血量、热量、允许发弹量和经济，并更新模拟器网页对应的输入项。
请处理实现这些功能所需的依赖和构建配置，保留现有可用的启动方式。
本次先完成基础数据准备和检查，真实 MQTT 接入留到第 2 步。
请逐项说明已更新和未更新的内容。协议本身不明确的地方单独记录，不要猜。
```

**你会看到什么，怎样算完成**

- 模拟器网页能够设置这批基础数据，编号和名称符合本赛季。
- Codex 已检查程序实际发送的数据与协议一致，不能只改网页上的文字。
- Codex 给出明确的已支持清单；尚未处理的功能保留为“未完成”。

这一步还不要求客户端收到网络数据。双方能真实收发，要在下一步验证。

### 第 2 步：让客户端通过 MQTT 真正收到数据、发出指令

**这一步做什么**

先接收，再发送。先通过简单测试页面显示真实收到的数字，然后选择一项基本操作验证发送，例如在满足条件的模拟场景中兑换允许发弹量。

**可以直接发给 Codex**

```text
请完成第 2 步：让客户端真正连接本地模拟器，通过 MQTT 接收并显示
第 1 步的基础数据。请提供简单测试页面，明确显示数据来自外部模拟器。
接收验证后，再实现一项协议明确的基本操作，优先测试兑换允许发弹量，
准备满足操作条件的模拟数据，并确认模拟器收到请求、处理后返回实际状态。
请分别检查“收到数据”和“发出指令”，同时检查停止服务和恢复后的表现。
如果需要补充对应协议或模拟器处理逻辑，请一起完成，不要只修改客户端。
```

**你会看到什么，怎样算完成**

- 在模拟器网页把某台机器人的血量改成 **321**，客户端对应机器人也显示 **321**。
- 停止数据发送后，客户端能提示数据已停止更新；恢复后继续更新。
- 在客户端发起测试操作，模拟器能看到收到的内容，随后客户端显示处理后的实际状态。

只显示“已连接”不算收到比赛数据。只让按钮变色、或点击后直接在客户端修改弹量，也不算发送成功。需要 Codex 查明两端的实际收发情况。

### 第 3 步：让客户端收到并播放 UDP 视频

**这一步做什么**

让模拟器发送一个测试视频，客户端接收后显示连续画面。所需软件和测试视频由 Codex 准备或检查。

**可以直接发给 Codex**

```text
请完成第 3 步：按项目中的 2027 协议修正模拟器视频发送格式，
并实现客户端的 UDP 视频接收和播放。先使用一个简单视频测试区域。
请检查连续播放、停止推流、重新推流，以及客户端中途启动后的表现。
视频异常时要有明确提示，不能让比赛数据或操作按钮一起卡住。
本次以正确播放为目标，正式视频区的布局和美化留到第 5 步。
```

**你会看到什么，怎样算完成**

- 模拟器开始推流后，客户端出现连续画面。
- 停止后显示无信号或断流提示；恢复后能重新播放。
- 播放一段时间后，画面没有越来越落后，软件也没有明显卡住。

Codex 还应检查视频数据缺失或到达顺序变化时的处理。只显示“收到多少个视频包”，不能算完成播放。

### 第 4 步：逐组增加比赛功能，同时更新三处程序

**这一步做什么**

每次只做一组功能，并同时处理：**客户端、模拟器内部处理、模拟器网页**。已有的基础数据和操作直接复用，不重复开发。

建议默认先完成步兵所需功能，再按队伍实际使用情况做其他组：

| 功能组 | 这次要能做什么 | 在模拟器里怎么检查 |
| --- | --- | --- |
| 步兵基本操作 | 性能选择、兑换、复活、远程补给，以及相关状态提示 | 设置允许或不允许操作的条件，检查请求和返回结果 |
| 键鼠操纵 | 按协议选择控制输入来源，将键盘和鼠标操作发给对端 | 模拟器能记录按键和鼠标状态；切离窗口或断线后不会延续旧按下状态 |
| 比赛总览 | 基地和前哨血量、控制度、阵地状态、事件、增益和判罚提示 | 网页逐项改值，核对客户端显示及对应对象 |
| 地图与指挥操作 | 机器人位置、路径、地图标记，以及协议允许的地图指令 | 改位置、切红蓝视角、发标记，检查有没有错人或错位置 |
| 哨兵 | 控制方式、姿态和允许的干预操作 | 发指令，查看处理结果和状态变化 |
| 重装 | 装配难度、步骤状态、确认和取消 | 从开始装配走到成功，再测试取消和失败 |
| 能量机关与飞镖 | 按协议和角色权限实现所需状态与操作 | 逐项测试状态变化、请求和不允许操作的情况 |
| 队伍自己的额外功能 | 例如机器人自定义状态或指令，仅在确有需要时加入 | 先明确机器人一端约定，再检查双方数据是否一致 |

“允许发弹量”是规则允许发射的数量，不代表机器人弹仓里的实际弹丸数量。

如果本队使用其他设备操纵机器人，应先告诉 Codex 由谁提供控制输入；终端不需要提供的操纵功能，可以明确记录为“本队不使用”。

**每次选一组，复制并改写第一句即可**

```text
这次只完成第 4 步中的“步兵基本操作”这一组。
请先检查已经实现的部分，补齐当前需要的功能，并按 2027 协议同时更新
客户端、模拟器内部处理和模拟器网页。测试页面能观察和操作即可。
请检查：网页修改后客户端同步、客户端请求后模拟器处理并返回状态、
不满足条件时不会显示成功，以及机器人编号和红蓝视角没有对应错误。
请列出本组已完成、尚未支持和仍需确认的项目，不要继续开发其他组。
```

**你会看到什么，怎样算完成**

这组功能能在模拟器里完整演示：网页能设置测试条件，客户端能显示和操作，模拟器处理后双方结果一致。Codex 已按协议检查数据；不会因为“两边都显示一样”就跳过协议核对。

第 2、3 步收到的真实数据，要在这里成为各项功能共同使用的数据。界面上没有收到的内容应显示“未收到”或“未知”，不能拿演示值冒充。

### 第 5 步：用模拟器完整测试，再完善正式界面

**这一步做什么**

先用测试界面走通完整比赛过程、修复问题，再确定正式布局。你可以描述想要的页面、提供参考图，并调整视频、地图、状态和操作区的位置。

这里可以通过模拟器按顺序设置测试场景完成，不要求先把真实比赛中所有运动和经济变化都自动模拟出来。

**可以直接发给 Codex**

```text
请开始第 5 步。先核对第 4 步哪些功能已经完成，使用现有模拟器和测试界面
检查准备、开赛、血量变化、兑换、战亡、复活和结算这一整段过程，
再检查数据中断恢复、视频中断恢复和连续两局比赛。
请先修复发现的问题，整理哪些通过、哪些失败、哪些没有测试。
这一轮先完成联调和问题修复，正式 UI 设计等我下一条消息再开始。
```

联调通过后，再发送：

```text
请根据已完成的功能设计正式 UI，先给我能看懂的页面布局草图和功能清单。
我会说明布局和操作偏好；确定后请实际实现，并继续用模拟器检查数据和操作。
把未完成或仍不明确的功能标出来，不要用假数据掩盖。
```

**你会看到什么，怎样算完成**

- 从准备阶段到结算，主要功能能连贯使用；第二局不会残留上一局的状态。
- 数据或视频中断时提示清楚，恢复后能继续使用。
- 正式界面里的数值来自实际接收的数据，按钮使用已经验证的发送功能。
- 布局能在目标屏幕上使用，操作方式符合你的需求；布局调整后再复测相关功能。

这里的“联调通过”只针对已明确支持并实际测试的功能。未开发的角色不能一起算作完成。

### 第 6 步：在目标电脑上运行，再和实车、官方接口联调

**这一步做什么**

把程序做成不需要安装开发工具也能运行的版本，在实际使用的电脑和设备上验证。Codex 协助程序、配置和问题定位；你和队友提供现场设备并执行实际操作。

**可以直接发给 Codex**

```text
请协助完成第 6 步：先把已通过模拟器测试的客户端打包，
让我能在目标 Windows 电脑上启动，不依赖开发环境。
再根据当前支持的功能，给出简单的设备连接、配置填写和测试顺序。
先验证真实数据和图传，再由现场人员逐项测试指令和控制。
请说明哪些你已在电脑上验证，哪些需要我连接现场设备后验证；
根据我反馈的现象和日志继续修复。没有真实设备证据的项目不要记成通过。
```

**你会看到什么，怎样算完成**

- 目标电脑能够启动程序。
- 实际机器人及官方设备的数据、视频、身份和操作结果正确。
- 用真实链路重测所支持的核心功能，影响这些功能的问题已解决；未解决的问题单独记录，对应项目仍标为“未通过”。

只和模拟器通信成功，不能算实车完成；只接上队伍自己的测试服务，也不能代替官方接口验证。真实设备暂时不可用时，应明确记录“等待现场验证”。

## 五、你不知道下一句怎么说时，可以直接这样发

**继续做下一项：**

```text
请阅读开发路线和进度记录，并核对实际代码，找到下一个尚未完成的小任务。
先用三句话说明这次会做什么、完成后我能看到什么，然后实际完成它。
完成后更新记录，明确已测和未测部分，不要一次推进整个项目。
```

**运行后有问题：**

```text
我在做第 __ 步。我先 __，再 __。
我原本希望看到 __，实际看到 __。
请结合项目和日志查原因并修复，告诉我修复后怎样重新检查。
```

你可以直接附上错误文字或截图，不需要先判断是哪一层代码的问题。

**还是听不懂：**

```text
请把这一步换成我能操作的说明：我打开什么、点哪里、应该看到什么。
技术术语先用普通话解释，代码和依赖选择由你负责。
```
